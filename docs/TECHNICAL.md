# How secret-protection-core works

This document describes what the crate applies on each system, what it does not cover, and how it is tested. The documentation of each public item says the same at the place of the code, with every system call named.

## Principles

- **A buffer protects itself, always.** Every buffer for secret bytes lives in pages of its own, is wiped before the pages are given back, never grows, and shows nothing of its bytes in its `Debug` text. No switch turns this off.
- **The whole process changes only when the program asks.** `Isolation::enter` changes the process for good and refuses things a general program needs, such as writing files. A library never calls it on its own.
- **What may stop a program or slow it is the program's choice.** A protection that a usual program could not work with, or that makes each use slower, is a type or an option the program takes, off by default; one whose cost is small is on, such as the speculation limits, which slow Argon2id by about 3 per cent.
- **Report, never pretend.** Each buffer says what the system confirmed when its pages were made, and `Isolation::enter` reads back every protection it applied: a field is true only when reading it back confirmed it. A refusal of the system is reported, never an error.
- **The calls of each system in a module of their own.** `unsafe` code lives only there, each block with the reason it is sound.

## A secret's pages

`Secret::with_capacity(bytes)` maps pages of its own for the buffer; `Secret::zeroed(bytes)` does the same and opens all of them for writing in place. The pages are zero when made. Its capacity is fixed: a `push` that does not fit is refused with `SecretError::Full` and writes nothing, so the buffer never moves and never leaves a copy behind. `truncate` wipes what it cuts, and dropping the buffer wipes every page before it is unlocked and given back.

| System                       | The pages                                                 | Out of swap     | Out of core dumps        | Out of a child process           |
| ---------------------------- | --------------------------------------------------------- | --------------- | ------------------------ | -------------------------------- |
| Linux on x86-64 and AArch64  | secret memory (`memfd_secret`), when the kernel offers it | by construction | by construction          | `MADV_DONTFORK`, checked         |
| Linux otherwise, and Android | a private anonymous mapping                               | `mlock`         | `MADV_DONTDUMP`          | `MADV_WIPEONFORK`: zeros         |
| macOS and iOS                | a private anonymous mapping                               | `mlock`         | no call for single pages | `minherit(VM_INHERIT_NONE)`      |
| Windows                      | a committed region                                        | `VirtualLock`   | error-report exclusion   | a new process maps nothing of it |
| WebAssembly                  | a heap buffer                                             | no              | no                       | no child processes               |

On every system but WebAssembly the pages lie between two guard pages that refuse every access: a reservation of the whole span that refuses access, whose middle is then opened (`mprotect`) or mapped over (secret memory, `MAP_FIXED`), and on Windows a reservation whose middle alone is committed. A run past either end of the pages faults instead of reaching other memory; a run within the last page, past the bytes asked for, does not. Linux and Android also mark anonymous pages unmergeable (`MADV_UNMERGEABLE`): should a parent have asked the kernel to merge every page of the process, which a child inherits, the time a write takes would tell a merged page.

Secret memory is kept out of the kernel's direct map: no other process, root included, reads it through `/proc/PID/mem`, `process_vm_readv` or `PTRACE_PEEKDATA`, and the machine does not hibernate while it exists. Its descriptor is opened with `O_CLOEXEC` and closed once the pages are mapped; every page is charged at once, so that a lock limit shows as a fallback to anonymous pages, not as a signal at the first write. A lock beyond `RLIMIT_MEMLOCK` leaves the pages as they are; Windows first grows the working set, under a lock that makes reading and setting it one step.

`is_locked`, `is_out_of_dumps` and `is_out_of_children` say what the system confirmed for these pages. On macOS no call keeps single pages out of a core dump: the process as a whole writes none once it is isolated. `Secret::locked(bytes)` refuses with `SecretError::NotLocked` pages that the system did not lock, before any byte is put in them, for a program that takes no secret into memory that could reach swap.

## A closed secret

`ClosedSecret` holds a `Secret` whose pages refuse every access between uses. Its bytes are reached only inside `read` and `write`, which open the pages for the call (`mprotect`, `VirtualProtect`) and close them again when it returns or panics; `push` and `truncate` open them the same way. A fault in another part of the program that reads memory it should not, as Heartbleed did, then meets a closed page and ends the process instead of reading the secret. The methods take `&mut self`, so that two uses never overlap; a system that refuses to open the pages again ends the process before any byte is reached, since a reference to closed pages would be undefined behaviour. `is_closed` says whether the last close took; in WebAssembly it is false. Each use costs two system calls, which is why it is a type of its own for the program to choose.

## The work area

`WorkArea::new(bytes)` gives the pages of a computation that holds secrets, such as the memory of Argon2id: the same as a secret's, guard pages included, but never secret memory, so that a large area does not keep the machine from hibernating. They are locked only when the lock limit holds all of them, which also commits them; a refused lock leaves them unlocked, and `WorkArea::is_locked` says so. `None` answers when the system refuses the pages. `WorkArea::locked(bytes)` refuses with `SecretError::NotLocked` an area that is not locked, and with `SecretError::NoMemory` when there are no pages: a program that requires the memory of its password hash locked then stops before it reads the secret, rather than computing with less memory.

## The isolation of the process

`Isolation::enter()` applies, for good, what the system offers against a secret leaving the process, and returns what reads back as holding. A program calls it before it reads a secret; a worker process that does only the work with the secret is the right place for it. Descriptors and handles opened before the call stay usable within the limits the table names.

| System                        | What it applies                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux                         | `RLIMIT_CORE` 0 (both limits), not dumpable, `no_new_privs`; speculative store bypass and indirect branch speculation disabled for good; on x86-64 and little-endian AArch64 a seccomp filter that refuses new sockets, io_uring, `ptrace` and `process_vm_readv`, changes of the file system, every `ioctl` but the terminal's, `connect`, `bind`, `listen`, `accept`, `sendmmsg` and `sendto` with an address through sockets opened before, System V IPC, POSIX message queues, the keyring, `execve`, `userfaultfd`, `bpf`, `perf_event_open`, the newer mount calls, and the `prctl` options that make the process readable again, and answers `ENOSYS` to newer calls; a Landlock layer where the kernel has it, made with the `landlock` crate, which also refuses connections to UNIX sockets and signals to processes outside it; network and IPC namespaces of its own when the process has one thread |
| Android                       | the same dump settings, speculation limits and filter, without Landlock and the namespaces, for the calling thread only, which must be a native thread of its own                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| macOS                         | `RLIMIT_CORE` 0, `ptrace(PT_DENY_ATTACH)` unless a debugger is already attached, a sandbox by least privilege that allows only reading files, writing the terminal, the process itself, system settings and the system's libraries                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| iOS                           | `RLIMIT_CORE` 0                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Windows                       | error reports without the heap; DLLs only from the program's folder and System32; no extension points, remote or low-integrity images, or child processes; side-channel isolation (branch targets, security domain, no page combining, no speculative store bypass); a job that refuses writing the clipboard, global atoms, other processes' windows, desktop and system changes; an access list of the process and of its threads that keeps other programs of the user out; low integrity                                                                                                                                                                                                                                                                                                                                                                                                                     |
| WebAssembly and other systems | nothing; every field is false                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

The filter and the Landlock layer are applied once per thread, and only what the kernel took is recorded: a further call finds the filter the thread already holds, from its own call or from the thread that started it, and adds no layer, so that the kernel's limits on filters and layers are not used up, while a filter or layer the system refused is tried again. The filter marks itself: it answers a `prctl` option that no kernel has with an error number of its own (4001), which the call reads before it installs anything. A filter that someone else installed, as every Android app and many containers run under, gives no such answer, and this crate's filter is added to it. The layer comes first, so that a thread that holds the filter holds the layer too; where no filter is written, what an earlier call of the thread or of the process recorded for the layer counts instead. The documentation of `Isolation::enter` names every call each system makes and what each does not cover.

Side effects a program should know about:

- **Linux:** after the network namespace is entered, `getuid()` and `getgid()` read 65534 for the rest of the process, since no ID map is written.
- **Android:** the filter holds for the calling thread only, which must be a native thread of its own: made with `pthread_create`, never attached to the Java virtual machine, reporting through shared memory rather than JNI, and ending with the work. A Java or Kotlin pool thread would go back to its pool restricted, its binder calls would fail, and the runtime's compaction calls `ioctl` from such a thread, which the filter refuses.
- **Windows:** every object the process creates afterwards without its own access list gets the restricted default list, so opening it again by name or ID, from the process itself too, grants little more than waiting for it; a thread cannot suspend itself or change its own context through `GetCurrentThread()`, as some runtimes need.

A field of the answer is true only when what it promises was confirmed. `no_file_changes` is true on Linux only where the filter holds, since Landlock alone leaves modes, owners, extended attributes and times, and false on Windows, whose low integrity level still writes where a low label allows it. `no_core_dumps` is false on Windows, whose error reports keep stacks and registers. `no_memory_reading` is false when a debugger or another tracer was attached before the call, as `TracerPid` and `CheckRemoteDebuggerPresent` say. `speculation_limited` reads back both kinds of speculation.

## Options and the strict mode

What does not keep a usual program from working is on without a switch: the buffers' protections always, and the isolation as soon as the program calls `Isolation::enter`. What may stop a program, or slows every use, is the program's choice and off by default:

| Protection                                           | On by default           | How it is turned on                                | Systems                             | Who needs it off                                         |
| ---------------------------------------------------- | ----------------------- | -------------------------------------------------- | ----------------------------------- | -------------------------------------------------------- |
| Pages of its own, wiped, guard pages, hidden `Debug` | always                  | `Secret`, `WorkArea`                               | all                                 | nobody                                                   |
| Locked, out of dumps and child processes             | where the system allows | `Secret`, `WorkArea`                               | all but WebAssembly                 | nobody                                                   |
| Pages refused unless locked                          | no                      | `Secret::locked`, `WorkArea::locked`               | all                                 | a program that would rather run unlocked than not at all |
| Pages closed between uses                            | no                      | `ClosedSecret`                                     | all but WebAssembly                 | a program that reads a secret many times a second        |
| The isolation of the process                         | when called             | `Isolation::enter`                                 | Linux, Android, macOS, iOS, Windows | a library, which must leave it to the program            |
| Speculation limits                                   | with the isolation      | `Isolation::enter`                                 | Linux, Android, Windows             | nobody: Argon2id slows by about 3 per cent               |
| File locks refused                                   | no                      | `Options::refuse_file_locks`                       | Linux, Android                      | SQLite and other databases                               |
| `sendmsg` refused                                    | no                      | `Options::refuse_sendmsg`                          | Linux, Android                      | Wayland, D-Bus, whatever passes descriptors              |
| No new executable code                               | no                      | `Options::refuse_dynamic_code`                     | Windows                             | web views and just-in-time compilers                     |
| Only DLLs signed by Microsoft                        | no                      | `Options::microsoft_signed_only`                   | Windows                             | the program's own DLLs, graphics drivers, input methods  |
| Signals only to the process itself                   | no                      | `Options::signals_to_self_only`                    | Linux, Android                      | a program that signals its children                      |
| The whole process out of swap                        | no                      | `Options::lock_all_memory`                         | Linux, Android                      | any program under the default lock limit                 |
| A protected stack for the secret work                | no                      | `run_on_protected_stack`                           | Linux, Android, macOS, iOS          |                                                          |
| Stop before the secret when a protection is missing  | no                      | `Isolation::enter_requiring`, `Isolation::require` | all                                 |                                                          |
| The secret work in a process of its own              | no                      | `Worker::start`, `serve`                           | Linux, macOS, Windows               | a program that keeps one process                         |

`Isolation::enter_with(options)` applies what `Isolation::enter` applies and the options as well; `Options::new()` turns none on, and each method of it turns one on. Each option reads back in a field of `Isolation` of its own (`file_locks_refused`, `sendmsg_refused`, `dynamic_code_refused`, `microsoft_signed_only`). On Linux the options are rules of the seccomp filter, and its mark names them: a thread that holds a filter without an option asked for gets a second filter with every option either call asked for, and a further call with the same options adds nothing.

`signals_to_self_only` adds filter rules: `kill`, `tgkill`, `rt_sigqueueinfo` and `rt_tgsigqueueinfo` only with the process's own number, no `tkill` or `pidfd_send_signal`. Landlock already blocks signals to other processes from Linux 6.12; this covers older kernels and Android. `lock_all_memory` calls `mlockall` with `MCL_ONFAULT`, so pages are locked as they are first touched; the kernel refuses it when the process's whole address space is above the lock limit, which under the default 8 MiB is almost always.

The strict mode names the protections a program cannot do without, as `Protection` values: `Isolation::enter_requiring(options, &required)` answers `Missing`, with every required protection that does not hold and what does, so that the program stops before it reads a secret. What was applied stays applied either way. `Isolation::require` checks an answer the program already has, as `Worker::start` does with the answer of its worker.

## The worker process

`Worker::start(options, &required)` starts the program again, from its own file, as a worker. The worker gets an empty environment but one variable, which names it a worker and carries the options; its standard input and output are pipes to the parent; on Linux and macOS it starts a session of its own, without a controlling terminal, and its standard error goes nowhere. Its `main` calls `serve` first: `serve` closes every descriptor but the standard streams (`close_range`, or each one /proc/self/fd or /dev/fd lists), calls `Isolation::enter_with(options)` while the process has one thread, and sends what read back as four bytes. Only then does the parent check `required`; when one is missing it closes the pipe, waits for the worker to end and answers `WorkerError::Missing`, and no request ever reaches the worker.

Requests and answers are frames: a length of four bytes, little endian, then the bytes. Each side reads a frame straight into a `Secret` (`Secret::zeroed` and `read_exact`, through descriptors without a buffer of the standard library), so that no copy of a secret stays behind in a buffer. `Worker::call(request, most)` refuses an answer longer than `most`, and every later call, as the rest of that answer still waits in the pipe. Dropping the worker closes its input, which ends `serve`, and waits for the process.

On Linux the worker gets the whole-process isolation: the filter, Landlock, the speculation limits, and network and IPC namespaces of its own where the system allows user namespaces. On macOS it enters the sandbox. On Windows the parent starts it with `CreateProcessW` in an AppContainer of its own, one per program, named after the program's path, without capabilities, so that Windows refuses it the network, the loopback address included, and the user's files; it inherits only the two ends of its pipes (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), has no console, and puts itself into the restricted job when it isolates itself. The program file and its folder must let every application package read and run them, as Program Files does; elsewhere Windows refuses the start. `Worker::start_on_terminal` keeps the terminal on Linux and macOS, for a worker that reads a password itself; it opens the terminal only for reading, since the filter refuses opening for writing, and prompts on its standard error. Android and iOS start no worker: an Android app that wants one declares an isolated service (`android:isolatedProcess`) in its manifest, and its native code isolates its own thread there.

What a request and an answer hold is the program's protocol. The worker should answer with what the parent shows or saves, such as a finished carrier and a report, never the password, the key or the secret itself, unless the parent is the one to show it.

## Looking closer

`open_channels()` lists every descriptor the process has open, standard streams included, as a socket, a file open for writing, a pipe, a terminal or something else (from /proc/self/fd or /dev/fd, `fstat` and the open flags). Isolation leaves what was open before usable, so this is the list of ways out the program itself chose. Windows has no plain way for a process to list its handles, and the answer there is `None`.

`Isolation::measures()` gives every protection with whether it holds, whether it reaches the thread or the whole process, and what confirmed it, such as "a new socket is refused" or "the side-channel policy reads back".

`run_on_protected_stack(bytes, work)` runs `work` on a new thread whose stack is a work area: guard pages, out of core dumps and child processes, locked where the limit allows, and wiped after the thread ends, so the secret's copies in local variables go with it. glibc puts the thread's own data and static TLS at the top of a stack it is given, so those land in the protected pages as well. Registers, the caller's stack and heap copies are not covered. Windows' `CreateThread` takes no stack from its caller, so it is not offered there.

## Typing a secret

Where a secret first appears decides what protects it. An ordinary text field keeps copies of what is typed in buffers of its toolkit or web view, in its undo history and for screen readers, which no program can find and wipe. So:

- **In the terminal**, the worker started with `Worker::start_on_terminal` reads the password itself: the parent never holds it.
- **In a window**, the field keeps no text. It sends each key the moment it is pressed, as a `Keystroke` (`Keystroke::Char`, `RemoveLast` for Backspace, `Clear`), through the program's own code to the worker, and keeps only how many characters there are, to draw dots. The worker collects the keys in a `SecretLine`, whose bytes live in protected pages. A paste goes the same way: the program's own code reads the clipboard and hands it to the worker, never to the field. The window process sees one character at a time, for a moment.
- **A small native dialog** that alone asks for the password and hands it to the worker, as GnuPG's pinentry does, keeps even single characters out of the main window, but looks like no part of the program: it is a stricter mode for a program that wants it.

A whole scenario, as a program with a window runs it: the window process starts the worker with the protections it requires, and the worker reports them; the person types the password into the field, which sends each key to the worker; the window sends the carriers; the worker derives the key, encrypts and hides, and answers with the finished carriers and a report; the window saves them. The password and the key never leave the worker. Not covered: the keyboard input passes through the window system, and under X11 every program of the user can read the keys.

## The secret writer

`write_secret(text)` writes to standard output past the standard library's buffer, which keeps the last bytes written and is never wiped: it flushes that buffer first, so that public output written before comes first, then writes the caller's bytes without a copy of its own. On a Windows console its UTF-16 copy lives in a `Secret`.

## What changed from the copies

The crate replaces two identical copies in `mhfe_core` and `stego-core`. Its first version moved them without changing what they do, with their tests, and then fixed five things a review found:

1. The macOS probe of file writes opened a predictable path with `File::create`, which could truncate a file, or the target of a link, at that path when the sandbox had not taken hold, and then removed the path. It now makes only a new file (`create_new`) and removes only what it made.
2. The descriptor of Linux secret memory was opened without `O_CLOEXEC`: a program that another thread started before the descriptor was closed would have got it.
3. The answers of `MADV_WIPEONFORK` and `minherit` were dropped, while the documentation promised that a child process gets none of the bytes. `is_out_of_children` now reports them.
4. Every call of `Isolation::enter` installed another seccomp filter and Landlock layer, which use up limits of the kernel. A thread that holds this crate's filter, from its own call or from the thread that started it, now gets no further layer. A filter that someone else installed does not count: the first check took any filter for this crate's, so that an Android app, which always runs under the system's filter, got none of this crate's.
5. Windows read the working set and set it again in two steps, so that threads making pages at once could lose a change, and every later drop gave back more than was taken. The two steps are now one, under a lock.

A probe of the channels out of an isolated process, run on Linux 7.0 in both an isolated thread and a process of one thread, then found what the copies left open, and the crate closes it: System V objects, which another program of the user saw by their key, and the keyring, from which another program read a test value; the dump flag, which code in the process could set again; datagrams through sockets opened before, from a process in an empty network too, since a socket keeps the namespace it was made in; signals to other processes; `execve`; and `userfaultfd`. The same review found that a refused filter was recorded as installed, so that a later call did not try again, and that the answer overstated some protections on Windows, on the Linux architectures without the filter and under a debugger.

## What is not covered

- Copies the program makes of a secret, stacks and registers, an image of the whole memory when the machine hibernates (except while Linux secret memory exists), and snapshots of a virtual machine.
- A process that ends without running its drops: built with `panic = "abort"`, ended by a signal, `abort` or `std::process::exit`. No `Secret` is wiped then; what keeps the bytes is that the pages are locked and out of core dumps, and that the system clears pages before it gives them to another process.
- Root, an administrator (`SeDebugPrivilege`), `CAP_SYS_PTRACE`, and a debugger or a `/proc/PID/mem` descriptor opened before the isolation; the answer says so for a debugger.
- On Linux, a socket connected before, which the program keeps on purpose, `sendmsg` on a socket opened before, whose address the filter cannot read, and file locks, which another program sees: both are to become options of their own, since Wayland, D-Bus and SQLite need them. Signals to other processes are refused from Linux 6.12 only.
- In a process isolated in one thread, the other threads, which share its memory.
- On Windows, the network, which only an administrator or a worker process in an AppContainer can close, and error reports, which still hold the threads' stacks and registers.
- On Android, the crash handler makes the process dumpable again for its tombstone.
- Covert channels that need no call the filter sees, such as the load of the processor or the timing of a shared cache.

## Tests

The unit tests check the buffers: what fits and what is refused, that truncating wipes, that the pages report locks, dump exclusion and child protection where each system gives them, that a zeroed secret is zero on every page, that guard pages lie on both sides of a secret and of a work area, that a closed secret opens only during a use and closes again after a use that panicked, and that `Debug` hides the bytes.

Two test programs have a `main` of their own, because the isolation needs a process of one thread and the counting allocator a process without other threads; each starts itself again in a role as a child process. `isolation` checks from outside that an isolated thread is refused every call the filter names and keeps what it needs; that a datagram with an address is refused through a socket opened before, while a socket connected before still sends; that the dump settings cannot be undone; that no signal reaches a process outside the layer; that `speculation_limited` says what the kernel reads back; that a process of one thread is isolated as a whole, with IPC objects of its own; that further calls read back the same and add no seccomp filter (as the kernel counts them in `/proc/thread-self/status`), nor a call in a thread that an isolated thread started; that a process started under a filter of someone else's still gets this crate's, once; that a filter the system refuses is reported missing and tried again; that a process with a tracer attached is not reported unreadable; that options refuse file locks and `sendmsg` with one more filter at most, and the strict mode names what is missing; that two threads that isolate themselves side by side get one filter each; that threads and a work area still work after it; and that a secret is written after the buffered public output. `secret_memory` checks where the pages lie as the system reports them (locked, `MADV_DONTDUMP`, secret memory), that a secret works under every lock limit and says whether it is locked, that the strict constructors refuse what the limit does not hold, and that under a quota partly used by another secret whatever they give is really out of swap, that a work area lies on pages of its own, and that six hundred secrets in a row each give back their error-report exclusion. `worker` starts the test program as its own worker and checks that it answers isolated, that it has no environment, descriptor or terminal of its parent's but its pipes, that it applies the options it is given, that a worker lacking a required protection is stopped before any request, and that an answer longer than allowed is refused.

The tests run on Linux, and each protection the review added was checked by removing it: a test fails for each. Clippy checks the crate for Linux, Android, macOS, iOS, Windows and WebAssembly; the code for the other systems is not run here, and the macOS profile and the Windows mitigations have yet to run on those systems.
