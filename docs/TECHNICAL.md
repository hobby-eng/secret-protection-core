# How secret-protection-core works

This document describes how each OS backend allocates pages, installs restrictions and verifies worker startup. For Rust signatures, errors and usage examples, see the [API description](API.md).

## A secret's pages

Storage is wiped across the allocation, including unused capacity. Debug formatting hides the contents.

Native allocations have an inaccessible guard page on either side of the usable pages. A guard catches access beyond a page boundary. The last usable page can extend beyond the requested capacity. The WebAssembly implementation uses a fixed-size allocation in linear memory.

| Allocation                       | Swap protection         | Dump exclusion                                      | What a child receives                                   |
| -------------------------------- | ----------------------- | --------------------------------------------------- | ------------------------------------------------------- |
| Linux `memfd_secret`             | Provided by the mapping | Provided by the mapping                             | No data mapping after ordinary `fork`                   |
| Linux or Android anonymous pages | `mlock`                 | `MADV_DONTDUMP`                                     | Zeros if `MADV_WIPEONFORK` succeeds                     |
| macOS or iOS anonymous pages     | `mlock`                 | Process-level core limit only                       | No data mapping if `minherit(VM_INHERIT_NONE)` succeeds |
| Windows committed pages          | `VirtualLock`           | Windows Error Reporting registration for the region | A newly launched process has its own address space      |
| WebAssembly heap                 | Host controls paging    | Host controls dumps                                 | The crate reports no child-exclusion guarantee          |

Windows registers individual regions with Windows Error Reporting. This leaves other dump mechanisms, thread stacks and registers outside that exclusion. [Allocation properties](API.md#allocation-properties)

### Linux secret memory

On x86-64 and AArch64 Linux, the allocator first tries `memfd_secret`. It opens the descriptor with `O_CLOEXEC`, maps and charges the pages, requires `MADV_DONTFORK` and closes the descriptor before returning. The mapping stays out of the kernel's direct map. Its presence also prevents system hibernation.

A fork gate keeps an ordinary `fork` from inheriting the open descriptor. Registering that gate requires a single-threaded process. Create the first secret or enter isolation before starting application threads if you need this backend. The allocator falls back to anonymous pages if the gate is unavailable, a signal mask cannot be installed, it cannot acquire the gate within 100 ms or the kernel refuses the mapping or its page charges.

For anonymous secrets and protected stacks, Linux requests small, unmergeable pages. These are advisory requests. Work areas can use transparent huge pages. A successful memory lock covers the allocated pages, including on the anonymous fallback. When the kernel joins a work area's pages into a huge page, or moves locked anonymous pages to compact memory, it copies them and frees the old pages without wiping them. Booting with `init_on_free=1` wipes freed pages, and `vm.compact_unevictable_allowed=0` keeps locked pages in place.

### Using buffers after fork

Unix allocations carry a generation number. The registered `pthread_atfork` handler changes it in a continuing child. An owner inherited from the parent then reports false for its memory protections. Its destructor skips the parent's mapping, and a fresh attempt to borrow its bytes aborts the child. The child can allocate and use a new secret of its own when the parent had one thread at the fork; after a fork from a process with threads the child may inherit a lock held by a thread that does not exist in it, so it should only call `exec` or `_exit`.

These checks govern the Rust owner. The OS decides what the mapping contains. If the request to exclude or zero the pages failed, the child can still inherit the original bytes. Require `is_out_of_children()` before storing the secret when this matters.

Leave pre-fork byte references unused in the child. If a `ClosedSecret` callback returns or unwinds there, its guard skips the parent's permission change. Raw `clone`, `_Fork` and a signal handler that forks and resumes an interrupted library call fall outside the ordinary `fork` contract.

## A closed secret

The page guard tracks the last permissions the OS granted. Each operation borrows the owner mutably, so safe Rust cannot overlap two callbacks on the same owner. The guard requests closure during normal return and unwinding. If the OS refuses to reopen pages, the guard checks whether the existing permissions allow the operation before creating a reference.

On Windows a lock and a closure exclude each other. Making a locked page inaccessible unlocks it: the call answers `STATUS_WAS_UNLOCKED`, the page leaves the working set for the modified list, and the page file can take it. `ClosedSecret::locked` therefore keeps its pages locked and open, and `is_closed()` is false. `ClosedSecret::with_capacity` closes them, and `is_locked()` is false from the first closing; opened again, the pages stay unlocked. [ClosedSecret API](API.md#closedsecret)

## The work area

Native work areas use guarded pages. Linux always uses anonymous memory for these allocations so large scratch buffers can use transparent huge pages. WebAssembly uses a fallible heap allocation. A work area is wiped on drop once it was lent for writing; one never lent is still the zeros the system made, and is given back untouched, as filling it in would bring a large unused reservation into memory. [WorkArea API](API.md#workarea)

## The isolation of the process

Enter isolation before accepting a secret. The call changes the running process or calling thread and can disable operations a GUI, database or network client needs. The application should choose the boundary. Each OS module attempts its own protections and records what it could confirm.

### Linux and Android

Linux lowers both core-size limits to zero and clears the dumpable flag. `NoCoreDumps` requires both checks because a kernel crash handler can pipe a dump to another process. For `NoMemoryReading` the crate also checks every visible thread for a tracer. If it cannot inspect the threads, or a PID namespace can hide an outside tracer, the result can be `Unknown`. An already attached tracer or a dumpable process yields `Refused`.

On little-endian x86-64 and AArch64 the crate installs a seccomp filter. Its rules cover new sockets and connecting, binding, listening and accepting on any socket, one opened before included, executable launches, filesystem changes, addressed datagrams, System V IPC, message queues, kernel keyrings and debugging interfaces. It also restricts `io_uring`, mount operations and device control calls. File reads and writes through some existing descriptors can still work, and so does opening a file for reading, `/proc/PID/mem` and `/proc/PID/fd` of another process included, as far as the kernel's own rules for attaching let the process: the filter adds nothing to them. An addressed datagram through a socket opened before is refused only with `refuse_sendmsg`. The exact system calls and argument checks are in the [filter source](../src/os/linux/seccomp.rs).

`NoNewSockets` and `NoNewPrograms` require a refused probe and evidence of the crate's filter. Refusal by a host policy alone can give `Unknown`. `NoFileChanges` requires both the filter and a refused open for writing. Landlock alone leaves some filesystem metadata operations available. The filter uses a private `prctl` response to recognize its rules and avoid installing identical filters again. The marker belongs to the 0.2 line: a filter of 0.1, which a program can hold too through another dependency, answers another one and lacks rules of this one, so it never counts as this version's. This marker assumes cooperative host policies. A filter that deliberately imitates the marker can invalidate the evidence.

Linux also requests the Landlock filesystem, network and IPC restrictions supported by the running kernel. On architectures without this crate's seccomp filter the Landlock layer can still operate. Where the kernel implements signal scoping, `SignalsWithinLayer` covers the caller and its descendants in that layer. Processes inside the layer can signal each other.

Linux clears the dumpable flag and the core limit before it enters a user namespace, and enters one only when the flag reads back as cleared. Inside a namespace the user owns, every process of that user holds CAP_SYS_PTRACE, which Yama's relational mode accepts, and only the cleared flag still keeps another process out of the memory.

The filter limits calls that act on a process to the caller, which names itself 0: resource limits (`prlimit64`), scheduling (`sched_set*`, `setpriority`), page placement (`move_pages`, `migrate_pages`) and the robust-list read. A number is refused even for the process itself, since a child of `fork` inherits the filter and the number would name its parent; so are thread numbers, which `pthread_setaffinity_np`, `pthread_setschedparam`, `pthread_setschedprio` and a `pthread_create` with an affinity or an explicit scheduling attribute pass, and which then fail with EACCES after isolation. `setpriority` is allowed only for the caller's process, never a process group or a user. It refuses `kcmp`, `process_madvise` and `ioprio_set`. Of terminal ioctls it allows reading and changing settings, reading the window size, and dropping the input waiting (`TCFLSH` with `TCIFLUSH`, never the output), so `TIOCSTI`, which types input, is refused. With `signals_to_self_only` it also refuses the `fcntl` owner commands (`F_SETOWN`, `F_SETOWN_EX`, `F_SETSIG`) and setting `O_ASYNC`, after which a terminal makes its foreground group the owner by itself; signal-driven I/O then fails even to the process itself, and so does `F_SETFL` on a descriptor that already has `O_ASYNC`, which keeps it. The job-control signals the kernel sends to a whole process group (SIGTTIN and SIGTTOU to a background group that reads its controlling terminal, changes its settings, or writes to it under `TOSTOP`) stay outside the rule; a worker has no controlling terminal. With `refuse_file_locks` it refuses leases and delegations (`F_SETLEASE`, `F_SETDELEG`) as well as locks. A process's name and command line stay readable by other local processes, and code running after isolation can change both.

With a single-threaded process, Linux attempts to create user, network and IPC namespaces together. `EmptyNetwork` requires the recorded namespace setup, no interfaces other than loopback in the listing, and an empty IPv4 routing table. A socket opened before entry retains its original namespace. The new user namespace has no UID or GID mapping, so the application may see overflow IDs. `WholeProcess` requires finding exactly one thread at the check, or that the filter, and the layer where there is one, reached every thread: by `Options::all_threads`, or by an earlier call made while the process had one thread, whose filter and layer every later thread inherited. In a multithreaded process the filter applies to the calling thread and threads it subsequently creates.

The filter and the Landlock layer hold for the thread that installs them and the threads it starts afterwards. A process that already has other threads at entry gets them on those threads only with `Options::all_threads` on Linux, which installs the filter with `SECCOMP_FILTER_FLAG_TSYNC` (Linux 3.17) and the layer with `LANDLOCK_RESTRICT_SELF_TSYNC` (Landlock ABI 8, Linux 7.0). Where the calling thread already holds them it installs them again only until they have reached every thread once, as each stacked filter runs on every call and the kernel takes at most 16 layers; a layer that granted folders is never put in again, as a second one would close them. The filter goes onto every thread only where the layer did, or where the calling thread holds no layer at all, as on a kernel without Landlock: its folder rules and its marks of a layer count on the layer, and would open writes on a thread without one. A layer TSYNC the kernel refuses, or a kernel below ABI 8, therefore leaves both on the calling thread. The layer's TSYNC replaces every other thread's layer and cannot be undone, and the kernel refuses the filter's TSYNC where a thread holds a filter the caller's does not descend from. So before the layer's TSYNC the call puts a filter that allows everything onto every thread with TSYNC: the kernel refuses it in just that case and then puts it nowhere, and the whole call stays on the calling thread. Once it went in, every thread's filters descend from the caller's, so the filter's TSYNC after the layer's fails only for another reason: the kernel's limit on filter instructions, or a thread that put in a filter of its own meanwhile. Then the layer stays on every thread and the filter on the calling thread, which the report says. The layer's TSYNC is tried once per process, after that call's own check: a later call that would need it again, whose threads may hold other filters by then, stays on the calling thread, while one that needs none, the layer being on every thread already, can still put the filter alone onto every thread, whole or not at all. So the allowing filter goes in once at most, and stays, one more on every thread, changing no answer. Where this crate writes no filter, on processors other than x86-64 and AArch64, nothing shows whether the threads' filters agree, and the layer stays on the calling thread. Where an earlier secret or isolation put the gate of secret memory in place, a fork on another thread waits until the layer is on every thread and recorded, unless the gate stays busy past its 100 ms; otherwise a child forked in that instant holds the layer but not its record, and could report folders granted that the layer refuses. Whatever falls short, the other threads only gain restrictions: the caller's earlier filters, the allowing one, and the caller's new layer in place of their own. No call can see whether another thread holds a Landlock layer of its own, which the layer TSYNC replaces: the option is for threads that hold none. Each protection reports `Reach::Process` only when what enforces it reached every thread, and `WholeProcess` only when the filter did and the layer did where there is one; with folders granted, `NoFileChanges` needs both, as the filter alone lets the folder writes through anywhere. Android ignores the option: an app's own threads, Binder's and the runtime's, would lose what the filter refuses. What TSYNC costs: the other threads lose new sockets, file changes, new programs and the rest in the middle of their work, and the layer replaces a Landlock layer another thread had of its own, which can be wider for that thread than its own was. The empty network and IPC namespaces still need one thread, and the speculation limit stays per thread.

On Linux and Android, isolation asks the kernel to force speculative store bypass and indirect branch speculation off for the calling thread and the threads it starts afterwards; a limit the kernel applies cannot be undone and can cost speed. `SpeculationLimited` requires the kernel to report that both are permanently disabled or that the CPU is unaffected. An enabled mechanism or one that can be re-enabled gives `Refused`. If neither returns such a state and a query fails, the result is `Unknown`. This can occur on AArch64.

Android uses the dump controls, speculation checks and supported seccomp filter. It does not enter the Linux desktop namespaces or Landlock layer. Use a dedicated native thread that exits when the work is done. A JVM thread returned to a pool would keep its restrictions, including limits on Binder and device calls. Android's crash reporting can change dumpability when writing a tombstone.

### Granted folders

`Isolation::enter_with_folders` grants folders that `WritableFolder::create` made new, each still that folder and empty at entry. On Linux the Landlock layer gets a rule beneath each folder for `MAKE_DIR`, `MAKE_REG`, `WRITE_FILE`, `REMOVE_FILE`, `REMOVE_DIR` and `REFER`; best-effort mode drops `REFER` on ABI 1, where Landlock refuses every move between folders. Landlock checks the real path after symbolic links, and with `REFER` it refuses a link or rename that would give a file more rights than it had, so a file from outside cannot be linked in to be written. A rule the kernel refuses leaves the layer without any. Only when the layer took the rules does the filter take the `FOLDERS` bit, which lets the calls that make, move and remove files through in narrow forms: the shape and mode of an open, the mode of `mkdir`, no flags on `linkat`, at most `RENAME_NOREPLACE` on `renameat2`. The filter checks no descriptor number: any directory opened for reading after isolation could be moved onto it with `dup2`, so the place is Landlock's alone. A process whose layer or filter is older than the call gets no folder, as both only narrow. macOS writes three rules per folder into the sandbox profile, by the path `F_GETPATH` gives at entry: `file-write-create` beneath it for regular files and folders only (`vnode-type`), `file-write-data` beneath it, and `file-write-unlink` beneath it but not of the folder itself; a path with `"` or `\` is not granted. A folder is granted only while its path still leads to the folder held and the folder is empty, and `FolderWrites` is confirmed only for the call whose layer or sandbox took the folders. As the macOS rule names a path, `is_private` there also follows the path as given, name by name and through each symbolic link: a link, or a folder a name is looked up in, that someone else could change makes it false. [Grant folders](API.md#grant-folders-for-writing)

### macOS and iOS

Both systems set and check the process core-size limit. They have no per-allocation dump-exclusion call in this crate.

On macOS, the library checks for a debugger before requesting `PT_DENY_ATTACH`. That is all `NoMemoryReading` confirms there: it stops `ptrace`, not `task_for_pid`, which macOS grants to a tool of the same user with the debugger entitlement where developer tools are turned on (`DevToolsSecurity`), unless the program runs with the hardened runtime and without `get-task-allow`. It requests a sandbox that permits reading files other than terminal devices (a name under `/dev` starting with `tty`, `pty`, `cu.` or `console`), writing data to `/dev/null` and to the process's own terminal, named by path from its standard streams, ioctls on that terminal, operations on the process itself and read-only system settings and executable mappings from system library directories. The profile grants ioctls on that terminal without naming them, so it does not rely on refusing `TIOCSTI`, input that the shell reads as the user's own, through a controlling terminal: a worker has none (`setsid`), and macOS refuses it there anyway (`EPERM` in CI). A worker has no controlling terminal; a process that isolates itself while it keeps one can still type into it. For sockets and file changes, a refused probe counts as confirmation only when the crate's profile was installed. The file probe uses exclusive creation, in the temporary folder, else `/private/tmp`, each only where it exists and lies outside the granted folders: a refusal other than the sandbox's tries the next place, and none left reads `Unknown`. If the creation succeeds, it tries to unlink the probe path. The profile denies starting a program, but the crate has no execution probe to confirm that measure. iOS uses the process core limit without installing the desktop sandbox. [Apple implementation and profile](../src/os/apple.rs)

### Windows

Process mitigation policies restrict extension points, image loading and child processes. The default DLL search includes the application directory and System32, so the application directory and its write permissions matter. Explicit paths or search flags can select a different location. `NoNewPrograms` requires a child-process policy with no exception for secure processes. A separate job applies desktop restrictions and an active-process limit of one. Side-channel isolation has its own policy readback.

Two protections depend on the process's threads:

1. For `NoMemoryReading`, the crate sets and checks the process and thread access lists and the default list for newly created objects. It reaches the calling thread through its pseudo handle and other threads by number: an AppContainer worker's first thread starts with the restricted list, which grants the worker's package nothing, so the worker could not open it by number. A thread that the worker starts after its default list changed starts with that list too, and one that appears between that change and the walk makes the measure read as not confirmed. It also checks for a debugger. Existing handles retain their granted rights. New access by name or thread ID, even by the process itself, can fail once the lists change.
2. For `LowIntegrity`, the crate checks the primary token and the effective tokens of the live threads after lowering integrity. A thread without an impersonation token uses the primary token. One observed token above low integrity refuses the measure. An unavailable thread list or an unreadable token cannot establish whole-process low integrity. These observations apply at the time of the check. A program can impersonate a different identity later.

Each check requires a complete thread list containing the caller. A standalone `Isolation::enter` uses its own view of the kernel process inventory. Windows can hide that inventory after the process lowers its privileges. A [worker](#the-worker-process) can ask its trusted parent for the list. The worker checks its own token through its thread's pseudo handle. The first pass opens every other listed thread by its number, checks with `GetProcessIdOfThread` that it belongs to this process, sets its access list and keeps the handle. The second pass, after the primary token is lowered, reads a sibling's effective token through the kept handle while a wait of zero time shows that thread alive, as a live thread keeps its number; a thread that ended in between is opened by number again, and its process checked again. [Windows thread checks](../src/os/windows/threads.rs) · [GetProcessIdOfThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessidofthread)

Low integrity still permits writes in locations that allow it. Windows Error Reporting receives a request to exclude the heap, without a policy readback. Accordingly, Windows leaves `NoFileChanges` and `NoCoreDumps` unsupported. For a worker, `NoNewSockets` checks the AppContainer token and absence of capabilities. The report describes token policy. It does not inspect loopback exemptions or try a socket connection.

### WebAssembly

The host controls paging, networking and dumps. The crate can wipe the bytes it owns in linear memory on normal drop. Process isolation measures are unsupported, and `with_cleared_stack` overwrites nothing: the crate cannot tell how much of the stack in linear memory is left below the work, and a clearing past its start traps where rustc puts the stack first, or reaches the program's data where another toolchain puts it there. The WebAssembly target also lacks native worker launch, page-access control and protected thread stacks.

## Options and the strict mode

The [API description](API.md#options) lists each optional restriction, its platform and its effect on callers.

`SignalsToSelfOnly` and Landlock's `SignalsWithinLayer` report separate facts. Only a verified filter rule naming the current process confirms the former. A child can request a new rule. Linux records successful whole-process memory locking in a page zeroed on fork, since a child does not inherit the lock. Without the marker an earlier lock may be unverifiable. If the application explicitly unlocks memory, the marker can still report an earlier successful lock on a later call.

The Windows dynamic-code check also requires that thread opt-out and remote downgrade are disabled. The Linux and Android whole-process lock uses on-fault locking for current and future mappings. [Report fields and outcomes](API.md#outcomes-scope-and-errors)

## The worker process

The launcher, executable and libraries running during initialization are part of the trust boundary, and so is the parent: the channel is as private as the parent process, which is not isolated. A process that may attach to the parent, with `ptrace` or on Linux `pidfd_getfd` where Yama allows it, can take its descriptors and read its memory. On Linux `exec` makes the worker dumpable again until it clears the flag in its isolation, and a process allowed to attach to it then could take its channel. The parent reads `kernel.yama.ptrace_scope` before it launches the worker and launches none unless it is 1 or more, which keeps every process of the user but the program's own ancestors away, and unless the program runs in the first user namespace: in a namespace its user owns, any process of that user holds the right to attach from outside, dumpable flag or not. A worker taken in that time could report anything. The start then fails with `WorkerError::Start` of kind `PermissionDenied`. [Worker API](API.md#run-a-worker)

1. The launcher creates private request and reply channels. On Unix these are the worker's standard input and output: on Linux two pairs of connected sockets, as another process of the same user may open a pipe of a process again through `/proc/PID/fd` but not a socket; on macOS pipes, as no other process can open another's descriptors there. Standard error is `/dev/null`, or for a worker on the terminal the program's terminal, opened anew by name for reading and writing without becoming a controlling terminal; never whatever the parent's standard error is, such as a log socket. Windows uses a local, single-instance named pipe and disables handle inheritance. Linux starts the worker from `/proc/self/exe`, the very file the parent runs; macOS and Windows start the file at the program's path.
2. At `serve` entry, Linux first requires one thread, as `/proc/self/status` counts them: another thread could open a descriptor after the inventory, or hold a descriptor table of its own, which the inventory does not read. Then Unix verifies that the serving thread sees no descriptors above standard error. This inventory does not establish the identity of descriptors 0–2. Failure to enumerate descriptors prevents a clean start. Windows relies on the launch-time inheritance setting. It does not enumerate handles opened by the worker's own code.
3. On Unix every worker leaves its parent's session, so it has no controlling terminal; a worker that cannot leave is not clean. A worker isolates itself alone, without `Options::all_threads`, which it ignores. It then enters isolation and sends its clean-start flag and per-protection results.
4. The parent reads the startup report before exposing the worker transport to the application.

### Launch and peer checks

On macOS, `POSIX_SPAWN_CLOEXEC_DEFAULT` closes inherited descriptors omitted from the spawn actions. On Linux, the launcher closes descriptors starting at 3 after redirecting the standard streams. The fallback uses `close_range` with `UNSHARE | CLOEXEC` in a separate launcher thread. If both mechanisms are unavailable, startup fails. Launch and collection run on an ordinary stack, including when the caller is working on a protected stack.

Windows launches the worker in an AppContainer with no network capabilities. The AppContainer profile, one for each program path, and its folder, where the worker's `TEMP` points, stay after the worker ends, to be used again. Threads that Windows starts in the worker before its census, such as the loader's, keep the token's default list until then, so another process of the user could open one in that time and keep the handle. The executable and its libraries must permit execution by application packages. The process and its first thread are created with the access lists that `NoMemoryReading` later checks, so another process of the same user cannot open them for memory access before the worker isolates itself. Once the parent has exchanged its creation handle for a limited handle, it holds only wait and termination rights on the worker process. It checks that the kernel-reported pipe client PID belongs to that worker. The worker checks the server PID against its creator and requires a separate random 128-bit launch nonce. The nonce is absent from the pipe name. Repeated local competition for the pipe can still prevent startup.

Before the first application request, the worker asks its parent for two fresh thread lists, one for the access-list check and one for the integrity check. The parent checks that its process handle still identifies a running worker throughout each inventory. The worker validates the lists and reads its own thread access rights and tokens. An unavailable list cannot satisfy a strict requirement for the corresponding protection.

The private startup setting takes known option bits in canonical unsigned decimal and a terminal flag. Windows adds the generated pipe name and launch nonce as separate fields and requires a zero terminal flag. Both the name suffix and nonce use 32 lowercase hexadecimal digits. A malformed setting returns `false` before `serve` claims the worker role. A recognized role with a failed startup returns `true` without serving application data. `Worker::start` refuses recursive startup when the role variable is already present. [Startup and frame parser](../src/worker.rs)

### Requests and shutdown

The transport prefixes the application's bytes with a four-byte little-endian length. With a deadline, Unix polls the channel before each read and before each write of at most `PIPE_BUF` bytes, which a pipe or a socket that reports room accepts without blocking. Windows pipes block, so a watchdog thread terminates the worker through its process handle when the deadline passes, and the blocked read or write then fails. On shutdown, Windows can terminate through its retained process handle. Linux can signal a pidfd obtained at spawn; a worker that ended by itself just before counts as ended. The worker keeps one request buffer, 4 KiB to start, wiped after each request, and gives it back before it takes a larger one. The POSIX fallback hands the child's wait status to a dedicated waiter. [Unix child lifecycle](../src/os/unix/child.rs) · [Request limits, errors and shutdown deadlines](API.md#run-a-worker)

## File descriptor enumeration

Linux enumerates descriptors through `/proc/thread-self/fd` because threads can have different tables. Apple platforms use `/dev/fd`. The listing can race opens and closes in another thread sharing the table. Shared memory carries data without a descriptor once it is set up, so the inventory lists it too: on Linux the mappings of `/proc/self/smaps` whose flags hold `sh` and `mw` (shared, may be written, after `mprotect` too), on macOS the regions that `proc_pidinfo` (`PROC_PIDREGIONPATHINFO`) reports with a highest protection that allows writing and whose writes reach a file or another holder, or with `VM_INHERIT_SHARE`, which `mmap` gives every `MAP_SHARED` mapping. A read-only shared mapping of a file opened for reading can never be written, so it is not listed. This crate's own secret memory, a shared mapping of `memfd_secret`, is left out by its address, not its name, which another program's secret memory could carry too. On macOS the share mode needs reading with care. Copy-on-write, empty and superpage regions are taken to reach no one, and so is a region whose object the system found only in this process (`SM_PRIVATE_ALIASED`). These are readings, not proofs: copy-on-write only means that the region's own object has another beneath it, and the region's object can itself be shared through a memory entry; the system reports physically contiguous memory as empty, and its own count of aliases is a guess. An object of a pager, such as a file's, mapped once with one more reference reads as private and keeps a count of 2, so a private region counts then. A file that this process alone maps reads as private too, with a count of 1 while it is written out, and so does a copy that holds all its pages, as dyld maps a program's data: only a copy has pages found above another object or swapped out of itself, so a private region of a file counts unless it has such pages. The system does not compare a truly shared object with the process's other regions, so the walk counts the regions that map each object, and such a region counts when its object has more references, which an allocator's guard pages, one object mapped twice, do not. While the system writes memory out, a walk can read one reference fewer, and memory that one other holder shares can then go unlisted. The buffer that `os_log` shares with the log daemon is left out when one region alone looks like it (tag `VM_MEMORY_GENEALOGY`, no file, `VM_INHERIT_NONE`, shared): entering isolation brings it in, as the sandbox logs, and writes there reach the system log, as `os_log` calls do. A region made to look the same cannot be told apart from it. So the macOS list names memory shared in the open; code in the process that hides a channel can stay off it. The macOS walk counts as complete only when it ended on `EINVAL`, past the last region, and covered the regions of its own code, stack and heap; any other error leaves it incomplete. On Linux this crate's own secret memory is left out only at a remembered start and under the name `/secretmem (deleted)`, as a child of `fork` may map other memory where a secret was; the starts sit in atomic slots, which `fork` copies safely. [Descriptor inventory API](API.md#inspect-open-channels)

## Protected thread stacks

The Unix stack backend joins the thread before wiping the entire supplied stack, including unused space. A failed join aborts because a live thread could still be writing to the stack. Forking while the thread runs can leave a child with a zeroed or missing stack or thread-local storage. [Protected stack API](API.md#protected-thread-stacks)

## Typing a secret

The GUI toolkit can still retain input events, and paste can expose an entire password through the clipboard. A terminal worker on Unix has the terminal as standard error but no controlling terminal, so it cannot type into it. It can still write any bytes there, including control sequences the terminal emulator acts on, and leave the terminal settings changed: the parent can save them before the start and restore them after. Landlock can prevent control operations on a terminal opened after isolation. [Input API and frame encoding](API.md#secretline-and-keystroke) · [Terminal workers](API.md#run-a-worker)

`read_hidden_line` reads a line on a terminal itself. On Unix it turns off echo, the terminal's line editing (`ICANON`, `IEXTEN`), its signal keys (`ISIG`), the signal a break condition raises (`BRKINT`), flow control (`IXON`), which would take Ctrl+S and Ctrl+Q, and the input changes that would drop a carriage return, the Enter key (`IGNCR`), or the eighth bit of a byte, which UTF-8 needs (`ISTRIP`), and reads the settings back; when any of them did not change, it refuses before reading anything, as it does for an input set not to wait (`O_NONBLOCK`). Before the prompt, and again before it restores the settings, it reads with `VMIN` 0 under its own settings, once they read back, whatever another program set meanwhile, and drops what it finds, up to 64 KiB, failing when more is waiting: keys the terminal showed or another program inserted, and what is left after Enter, such as the rest of a pasted text that the shell would read next. On Linux such a read first takes in input still on its way through the terminal driver, and waits while another process is blocked reading the same terminal. After a reading that ended as it should, the restore drops what arrived after that read with `tcflush` just before the change, as `TCSAFLUSH`, which does both at once, first waits until all output is sent, and a terminal whose output is stopped never sends it. A key typed in the moment between the two calls, and input that arrives after the restore, goes to the next reader. The restored settings are read back too, speeds included, all but the two bits the terminal changes by itself: `PENDIN`, which macOS sets when line editing comes back on, and `FLUSHO`, which Ctrl+O switches there and which drops all output while it is on. Neither the hidden settings nor the restored ones set them again, so a Ctrl+O typed before the reading drops neither the prompt nor what follows. It reads one byte at a time into the protected line, assembling UTF-8 in a four-byte buffer it wipes, and the 16 KiB of stack below its frame are wiped after, as `with_cleared_stack` does with 128 KiB; the terminal driver's buffers in the kernel are beyond its reach. With `ISIG` off, Ctrl+C, Ctrl+Z and Ctrl+\ arrive as keys, so every way out of the reading passes the code that restores the terminal; only a signal from another process can end the program with the echo off. It reads standard input when that is a terminal open for reading, else standard error, where a worker on the terminal has it, and opens nothing, so it works after isolation: the filter allows the terminal's settings requests and the flush of its input, and Landlock does not restrict descriptors opened before it. On Windows it clears `ENABLE_ECHO_INPUT`, `ENABLE_LINE_INPUT` and `ENABLE_PROCESSED_INPUT` on the console of standard input, reads the mode back, flushes the console's input before and after, the second time just before the mode comes back, so that a key typed between the two calls goes to the next reader, failing when it cannot, reads the restored mode back, and reads UTF-16 units with `ReadConsoleW`; Ctrl+Break stays a signal. A Windows worker has only a hidden console of its own (`CREATE_NO_WINDOW`), which nobody types into, so there the parent reads the line. [Hidden input](API.md#hidden-terminal-input)

What a worker on the terminal can do there besides reading its own line: having left the parent's session, it is not stopped by the kernel's job control, so the worker of a program in the background competes with the shell for keys. While it lives it can read keys typed for the parent, flush the terminal's input, change the settings, for example make a common letter the interrupt key so that the user's typing sends signals to the foreground job, and write control sequences that make the terminal send replies the next reader takes as typed input. The filter cannot see the contents of a settings request, so it has no narrower rule; a program that does not trust its worker with the terminal starts it with `Worker::start`.

## The secret writer

Direct writes preserve the order of earlier buffered output by flushing first. On Windows a console is a handle that `GetConsoleMode` accepts, or a character device for which it answers access denied, as a console open only for writing does; for it the backend converts UTF-8 to UTF-16 in a temporary `Secret`. Other Windows output, a file, a pipe or NUL, uses `WriteFile`. [Standard output API](API.md#standard-output)

## What is not covered

- **Other copies.** A `Secret` wipe covers its own allocation. The caller's input string, clipboard, GUI events, registers and copies in other processes or snapshots have separate lifetimes. Privileged access, a previously opened memory handle or a hypervisor snapshot can still expose data.
- **Exit without destruction.** A fatal signal, `abort` or `std::process::exit` can skip Rust destructors. Page locking and dump exclusion then depend on what the OS granted. This crate's standalone release profile uses abort-on-panic. The consuming workspace chooses the profile when it builds the crate as a dependency.
- **Existing channels.** A worker or sandbox can still use the channels retained for its work. A file opened for writing or a connected socket may carry data out. On macOS the system log stays reachable through the buffer `os_log` shares with the log daemon, which entering isolation brings in; `open_channels` does not list it. Mach ports made before isolation, such as an XPC connection's, stay usable too, and `open_channels` lists none. An `io_uring` ring created before isolation keeps running requests, and with a polling kernel thread (SQPOLL) without any system call the filter could refuse; `open_channels` lists it as `Other`. A worker's clean start admits no such descriptor. A trusted application must control what its handler sends back, what earlier initialization opened and which channels it permits.
- **Other threads and side channels.** Threads in the same process share memory. Thread-local restrictions leave existing peers free to perform their own operations. Speculation controls address specific CPU features. The crate does not measure or close channels based on scheduling, shared caches or timing.
