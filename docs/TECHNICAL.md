## Principles

- A secret buffer has a fixed capacity, hides its contents in `Debug` and wipes its storage on drop. Native buffers use private allocations with guard pages. WebAssembly uses a heap buffer in linear memory.
- The application decides when to enter isolation. Run it in a dedicated process when the rest of the application needs file writes, a GUI, networking or child processes. On Linux several restrictions apply to the calling thread and its future children.
- The caller opts in to closed pages, Microsoft-signed DLLs only, full-process memory locking and other measures with additional costs or compatibility limits.
- A buffer reports which protections the OS granted when it was allocated. An isolation report records the kernel response, policy state or probe used for each outcome. A strict call can reject missing protections before the application reads a secret.
- Platform-specific modules contain the operating-system calls and document the safety requirements of each unsafe block.

## A secret's pages

`Secret::with_capacity(bytes)` creates an empty, fixed-capacity buffer. `Secret::zeroed(bytes)` makes the full length available as zeros. `push` refuses an append that would exceed capacity, leaving the buffer unchanged. Truncation wipes the removed bytes. Dropping a buffer in its owning process wipes its entire allocation with `zeroize` before releasing it.

| System                       | The pages                                                 | Out of swap     | Out of core dumps        | Out of a child process           |
| ---------------------------- | --------------------------------------------------------- | --------------- | ------------------------ | -------------------------------- |
| Linux on x86-64 and AArch64  | secret memory (`memfd_secret`), when the kernel offers it | by construction | by construction          | `MADV_DONTFORK`, checked         |
| Linux otherwise, and Android | a private anonymous mapping                               | `mlock`         | `MADV_DONTDUMP`          | `MADV_WIPEONFORK`: zeros         |
| macOS and iOS                | a private anonymous mapping                               | `mlock`         | no call for single pages | `minherit(VM_INHERIT_NONE)`      |
| Windows                      | a committed region                                        | `VirtualLock`   | error-report exclusion   | a new process maps nothing of it |
| WebAssembly                  | a heap buffer                                             | no              | no                       | no child processes               |

On every system but WebAssembly the pages lie between two guard pages that refuse every access: a reservation of the whole span that refuses access, whose middle is then opened (`mprotect`) or mapped over (secret memory, `MAP_FIXED`), and on Windows a reservation whose middle alone is committed. A run past either end of the pages faults instead of reaching other memory; a run within the last page, past the bytes asked for, does not. Linux and Android also mark anonymous pages unmergeable (`MADV_UNMERGEABLE`): should a parent have asked the kernel to merge every page of the process, which a child inherits, the time a write takes would tell a merged page. For a secret's anonymous pages the kernel is also asked to keep them small pages (`MADV_NOHUGEPAGE`), since it copies pages when it joins them into a huge one and frees the old ones as they are; a kernel without huge pages refuses, and the answer is not read.

Linux secret memory stays out of the kernel direct map and prevents hibernation while it exists. The crate opens the descriptor with `O_CLOEXEC`, maps and charges every page, sets `MADV_DONTFORK`, then closes the descriptor. A gate excludes ordinary `fork` while the descriptor is open. Its handlers can be registered at the first allocation or isolation call while the process has one thread. If another thread already exists, registration fails, signal masking fails or a busy gate cannot be acquired within 100 ms, the allocator falls back to anonymous pages. It also falls back when the kernel refuses the mapping or charging. An anonymous allocation attempts `mlock`. Check the result before storing a secret that must stay out of swap.

`is_locked`, `is_out_of_dumps` and `is_out_of_children` say what the system confirmed for these pages. On macOS no call keeps single pages out of a core dump: the process as a whole writes none once it is isolated. `Secret::locked(bytes)` refuses with `SecretError::NotLocked` pages that the system did not lock, before any byte is put in them, for a program that takes no secret into memory that could reach swap.

After an ordinary Unix `fork`, the child receives copies of the Rust owners. The generation counter marks them as belonging to the parent. Their normal destructors skip wiping and unmapping, their protection queries return false, and attempting a fresh byte access through the owner aborts the child. A new buffer allocated by the child belongs to the child. When fork exclusion succeeded, a child receives zeros on Linux anonymous pages or no data mapping for Linux secret memory and Apple pages. When the OS refused exclusion, the child can retain the original bytes. Generation checks do not erase such an inherited copy. Check `is_out_of_children()` before storing sensitive data.

A continuing Unix child must leave every pre-fork byte reference unused. Its closed-secret callback can return or unwind safely: the guard checks its fork generation before changing page permissions. These guarantees require a normal fork and the registered child handler. Raw `clone`, `_Fork` and resuming an interrupted library call after a fork in a signal handler are outside this contract.

## A closed secret

`ClosedSecret` holds a `Secret` whose pages refuse every access between uses, as far as the system closes them: `is_closed` says whether they are closed now, and a program that relies on it looks after each use. Its bytes are reached only inside `read` and `write`, which open the pages for the call (`mprotect`, `VirtualProtect`) and close them again when it returns or panics; `push` and `truncate` open them the same way. A fault in another part of the program that reads memory it should not, as Heartbleed did, then meets a closed page and ends the process instead of reading the secret. The methods take `&mut self`, so that two uses never overlap. The secret remembers what its pages allow as the system last confirmed it: after a refused close they stay open, `is_closed` says so, and later uses work, with the next close counting again. When the system refuses to open them and what they allow cannot serve the use, the process ends before any byte is reached, since a reference to closed pages would be undefined behaviour. In WebAssembly `is_closed` is false. Each use costs two system calls, which is why it is a type of its own for the program to choose.

## The work area

`WorkArea::new(bytes)` allocates zeroed scratch space, with a minimum length of one byte. Native work areas have guard pages. On Linux they use anonymous memory and allow transparent huge pages. WebAssembly uses the ordinary heap. The call returns `None` when the allocation fails. Check `is_locked()` before working with a secret that must stay out of swap, or call `WorkArea::locked(bytes)`. The latter returns `NotLocked` for an unlocked allocation and `NoMemory` for an allocation failure.

## The isolation of the process

`Isolation::enter()` applies, for good, what the system offers against a secret leaving the process, and returns what reads back as holding. A program calls it before it reads a secret; a worker process that does only the work with the secret is the right place for it. Descriptors and handles opened before the call stay usable within the limits the table names.

| System                        | What it applies                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux                         | `RLIMIT_CORE` 0 (both limits), not dumpable, `no_new_privs`; speculative store bypass and indirect branch speculation disabled for good; on x86-64 and little-endian AArch64 a seccomp filter that refuses new sockets, io_uring, `ptrace` and `process_vm_readv`, changes of the file system, every `ioctl` but the terminal's, `connect`, `bind`, `listen`, `accept`, `sendmmsg` and `sendto` with an address through sockets opened before, System V IPC, POSIX message queues, the keyring, `execve`, `userfaultfd`, `bpf`, `perf_event_open`, the newer mount calls, and the `prctl` options that make the process readable again, and answers `ENOSYS` to newer calls; a Landlock layer where the kernel has it, made with the `landlock` crate, which also refuses connections to UNIX sockets and signals to processes outside it; user, network and IPC namespaces of its own, entered in one call, when the process has one thread |
| Android                       | the same dump settings, speculation limits and filter, without Landlock and the namespaces, for the calling thread only, which must be a native thread of its own                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| macOS                         | `RLIMIT_CORE` 0, `ptrace(PT_DENY_ATTACH)` unless a debugger is already attached, a sandbox by least privilege that allows only reading files, writing the terminal, the process itself, system settings and the system's libraries                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| iOS                           | `RLIMIT_CORE` 0                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Windows                       | error reports asked to leave out the heap (`WerSetFlags`, not read back); the default search for DLLs limited to the program's folder and System32; no extension points, remote or low-integrity images, or child processes; side-channel isolation (branch targets, security domain, no page combining, no speculative store bypass); a job that refuses writing the clipboard, global atoms, other processes' windows, desktop and system changes; an access list of the process and of its threads that keeps other programs of the user out; low integrity                                                                                                                                                                                                                                                                                                                                                                               |
| WebAssembly and other systems | nothing; every field is false                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

Linux records the Landlock rights accepted by the kernel and installs the filter after the layer. On supported architectures, subsequent calls recognize a private `prctl` probe response whose low bits describe the rules and Landlock scopes already installed. This lets a thread and its descendants avoid stacking identical filters. An ordinary pre-existing policy that denies the probe with a different result does not count. The marker is a convention among cooperative filters. A host that deliberately supplies an identical response can invalidate this evidence. On architectures without this filter, the crate relies on the layer recorded for the thread or process.

Side effects a program should know about:

- **Linux:** after the network namespace is entered, `getuid()` and `getgid()` read 65534 for the rest of the process, since no ID map is written.
- **Android:** the filter holds for the calling thread only, which must be a native thread of its own: made with `pthread_create`, never attached to the Java virtual machine, reporting through shared memory rather than JNI, and ending with the work. A Java or Kotlin pool thread would go back to its pool restricted, its binder calls would fail, and the runtime's compaction calls `ioctl` from such a thread, which the filter refuses.
- **Windows:** every object the process creates afterwards without its own access list gets the restricted default list, so opening it again by name or ID, from the process itself too, grants little more than waiting for it; a thread cannot suspend itself or change its own context through `GetCurrentThread()`, as some runtimes need.

### What the answer says

Each protection comes back with an `Outcome`, which `Isolation::outcome` gives; a field of the answer is true only for `Confirmed`.

| Outcome        | Meaning                                                                |
| -------------- | ---------------------------------------------------------------------- |
| `Confirmed`    | in effect, and the call observed it                                    |
| `Refused`      | tried or checked, and not in effect                                    |
| `NotRequested` | an option the call did not turn on, and that was not in effect before  |
| `Unsupported`  | not offered on this system                                             |
| `Unknown`      | it may be in effect, but the system gave the call no way to confirm it |

What decides each one:

- `no_core_dumps`: on Unix the limit reads back 0, and on Linux the process is not dumpable. Not offered on Windows, whose error reports keep stacks and registers; `Isolation::enter` asks Windows Error Reporting to leave the heap out, which has no entry of its own.
- `no_memory_reading`: Linux checks dumpability and the tracer of each thread. The result is unknown if a thread cannot be inspected or the process is in a noninitial PID namespace, where an outside tracer can be invisible. Windows checks debugger status and access controls for the process, threads and newly created objects. Changing the access lists does not invalidate a process or thread handle previously granted to another program. macOS requests debugger-attachment denial before entering its sandbox.
- `no_new_sockets`: on Linux and Android, a refused socket probe counts only when this crate’s filter is present. On macOS the probe also requires the crate’s sandbox profile. On Windows the evidence is an AppContainer token without capabilities. That outcome describes the token policy. It does not establish whether a particular socket call failed, a loopback exemption exists or an existing channel can communicate.
- `no_file_changes`: confirmed on Linux and Android where the filter holds and opening for writing is refused. Without the filter it is refused, whatever else refuses a write: Landlock alone leaves modes, owners, extended attributes and times. Not offered on Windows, whose low integrity level still writes where a low label allows it. On macOS as for sockets, with a probe that makes a file.
- `no_new_programs`: on Linux and Android the filter refuses `execve`, probed with a path that names no file, and as for sockets a refusal without the filter is unknown; on Windows the child-process policy reads back without its exception for secure processes. On macOS the sandbox profile allows no new program, but no probe confirms it yet: unknown.
- `speculation_limited`: both kinds read back off for good, or the processor needs no limit. Unknown where the kernel gives a program no control of one of them, as Linux on AArch64 does for indirect branches: a program must not require it there.
- `whole_process`: Linux checks whether the calling process has exactly one thread. An unreadable thread list cannot establish this. Apple and Windows report process-wide scope for the protections they implement. Inspect the individual outcomes as well.
- `no_planted_libraries` (Windows): the crate checks extension-point and image-load policies and limits the default DLL search to the application directory and System32. A caller can select another path or search flags. The application directory remains a search location, so its contents and write permissions must be trusted.
- `desktop_restricted` (Windows): the job the process is in reads back with every limit of the desktop and with one process allowed, a second line behind the child-process policy. That limit binds the processes in the job; a job that lets a process leave it does not hold that process.
- `low_integrity` (Windows) requires a low or lower primary token. After lowering it, the library enumerates the process threads and checks each impersonation token. An observed higher level refuses the measure. An incomplete inspection cannot confirm it. The result describes the inspected tokens at the time of the check. An application can impersonate another identity later. Comparing the saved handle with the live thread object requires Windows 10 or Windows Server 2016 or newer. [Microsoft’s CompareObjectHandles requirements](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-compareobjecthandles).

## Options and the strict mode

What does not keep a usual program from working is on without a switch: the buffers' protections always, and the isolation as soon as the program calls `Isolation::enter`. What may stop a program, or slows every use, is the program's choice and off by default:

| Protection                                          | On by default           | How it is turned on                                | Systems                             | Who needs it off                                         |
| --------------------------------------------------- | ----------------------- | -------------------------------------------------- | ----------------------------------- | -------------------------------------------------------- |
| Fixed capacity, wipe on drop, redacted `Debug`      | always                  | `Secret`, `WorkArea`                               | all                                 |                                                          |
| Dedicated allocation between guard pages            | always on native hosts  | `Secret`, `WorkArea`                               | Linux, Android, macOS, iOS, Windows |                                                          |
| Locked, out of dumps and child processes            | where the system allows | `Secret`, `WorkArea`                               | all but WebAssembly                 | nobody                                                   |
| Pages refused unless locked                         | no                      | `Secret::locked`, `WorkArea::locked`               | all                                 | a program that would rather run unlocked than not at all |
| Pages closed between uses                           | no                      | `ClosedSecret`                                     | all but WebAssembly                 | a program that reads a secret many times a second        |
| The isolation of the process                        | when called             | `Isolation::enter`                                 | Linux, Android, macOS, iOS, Windows | a library, which must leave it to the program            |
| Speculation limits                                  | with the isolation      | `Isolation::enter`                                 | Linux, Android, Windows             | nobody: Argon2id slows by about 3 per cent               |
| File locks refused                                  | no                      | `Options::refuse_file_locks`                       | Linux, Android                      | SQLite and other databases                               |
| `sendmsg` refused                                   | no                      | `Options::refuse_sendmsg`                          | Linux, Android                      | Wayland, D-Bus, whatever passes descriptors              |
| No new executable code                              | no                      | `Options::refuse_dynamic_code`                     | Windows                             | web views and just-in-time compilers                     |
| Only DLLs signed by Microsoft                       | no                      | `Options::microsoft_signed_only`                   | Windows                             | the program's own DLLs, graphics drivers, input methods  |
| Signals only to the process itself                  | no                      | `Options::signals_to_self_only`                    | Linux, Android                      | a program that signals its children                      |
| The whole process out of swap                       | no                      | `Options::lock_all_memory`                         | Linux, Android                      | any program under the default lock limit                 |
| A protected stack for the secret work               | no                      | `run_on_protected_stack`                           | Linux, Android, macOS, iOS          |                                                          |
| Stop before the secret when a protection is missing | no                      | `Isolation::enter_requiring`, `Isolation::require` | all                                 |                                                          |
| The secret work in a process of its own             | no                      | `Worker::start`, `serve`                           | Linux, macOS, Windows               | a program that keeps one process                         |

`Isolation::enter_with(options)` applies what `Isolation::enter` applies and the options as well; `Options::new()` turns none on, and each method of it turns one on. Each option reads back in a field of `Isolation` of its own (`file_locks_refused`, `sendmsg_refused`, `dynamic_code_refused`, `microsoft_signed_only`, `signals_to_self_only`, `memory_locked`); an option that holds from an earlier call reads as confirmed whether or not this call asked for it, and one that neither holds nor was asked for as not requested. On Linux a file lock or a `sendmsg` that is refused confirms its option only when the filter the thread holds has the rule; refused without the rule, by someone else's policy, it reads as unknown. `dynamic_code_refused` counts only without a way out: a policy that lets a thread opt out or another process lift it does not hold. On Linux the options are rules of the seccomp filter, and its mark names them: a thread that holds a filter without an option asked for gets a second filter with every option either call asked for, and a further call with the same options adds nothing.

Signals have two protections. `signals_to_self_only` is the option: filter rules that allow `kill`, `tgkill`, `rt_sigqueueinfo` and `rt_tgsigqueueinfo` only with the process's own number and refuse `tkill` and `pidfd_send_signal`. The filter itself answers whom its rule names, to the thread that asks: no thread reports the rule of another thread. A child made by `fork` inherits the rule with its parent's number and does not report the protection until it asks for it, which gives it a filter of its own; a filter that the kernel then refuses leaves it unreported. `signals_within_layer` needs no option: from Linux 6.12 the Landlock layer keeps signals inside it, which still reaches the children the process starts afterwards. It is confirmed only when the layer itself went in with that scope, not because the filter did.

`lock_all_memory` calls `mlockall` with `MCL_ONFAULT`, so pages are locked as they are first touched; the kernel refuses it when the process's whole address space is above the lock limit, which under the default 8 MiB is almost always. A lock that took is reported by later calls of the same process: its mark lies on a page that a child made by `fork` gets as zeros, so a child, which inherits no lock, does not report one, whatever its number. Where the system gives no such page, as before Linux 4.14, a lock taken by an earlier call reads as unknown. The program itself can still unlock its memory, which nothing here refuses.

The strict mode names the protections a program cannot do without, as `Protection` values: `Isolation::enter_requiring(options, &required)` answers `Missing`, with every required protection that is not confirmed and what is, so that the program stops before it reads a secret. Refused, not requested, not offered and unknown all count as missing. What was applied stays applied either way. `Isolation::require` checks an answer the program already has, as `Worker::start` does with the answer of its worker.

## The worker process

`Worker::start(options, &required)` launches the current executable. Protect the executable and the libraries it loads from replacement. On Linux and macOS, the worker uses standard input and output for its pipes and redirects standard error by default. The Unix launch runs on a separate thread with an ordinary stack. On Windows the worker has no standard handles and uses one named pipe. The ordinary worker receives its role and options in an environment variable. Windows also supplies the system and container paths needed to start the process.

Call `serve(most, answer)` first in `main`. The options field accepts canonical unsigned decimal digits and known bits only. Unix requires exactly two fields and a terminal flag of 0 or 1. Windows requires a zero terminal flag and the generated pipe prefix followed by 32 lowercase hexadecimal digits. Invalid syntax returns false before claiming the worker role. A valid role whose transport fails to open returns true and serves no requests. `Worker::start` refuses recursive startup when the role variable is present.

On macOS, `POSIX_SPAWN_CLOEXEC_DEFAULT` closes descriptors that the spawn actions do not name. Linux appends a child-side close-from action after redirecting standard streams. When libc lacks this action, a temporary launcher uses `close_range(UNSHARE | CLOEXEC)` before spawning. If neither mechanism works, startup fails. From program initialization onward, the worker executable and its libraries are trusted. At entry to `serve`, Linux uses `/proc/thread-self/fd` to check the calling thread’s own table, including when it differs from the thread-group leader’s table.

The worker performs these steps before reading its first request.

1. On Unix, check the current open descriptors. Any descriptor still open above standard error, or a failure to enumerate, prevents a clean report. Windows starts the worker with handle inheritance disabled and skips this enumeration.
2. On Linux and macOS, call `setsid` unless the parent chose `Worker::start_on_terminal`.
3. Call `Isolation::enter_with(options)`. Linux checks the thread count at this point. A library initializer or application that started a thread earlier can leave some protections scoped to the serving thread.
4. Send the startup check and each protection’s outcome and scope. Both worker and parent require whole-process isolation before accepting requests.

The parent finishes reading and validating the report before releasing a `Worker` to the application. An unclean start produces `WorkerError::Unclean`; a missing required protection produces `WorkerError::Missing`. Failure to start or read the report produces `WorkerError::Start`. On these paths the parent sends no secret request and attempts cleanup.

Each request and reply begins with a four-byte little-endian length. The worker checks a request against the `most` passed to `serve` and the parent checks a reply against the limit passed to `call`. Accepted frames are read into fixed-capacity `Secret` buffers. Their locks depend on the OS and the process lock limit. On Unix, leaving `serve` redirects the worker streams to /dev/null or an ended pipe, or closes the originals if redirection fails. On Windows it closes the pipe.

A failed exchange closes the transport and prevents further calls. `end` allows one second for cooperative exit. Windows and Linux with a spawn-time pidfd can terminate a stubborn worker and wait up to one second more. macOS and Linux without pidfd support return false at the first deadline if the child still lives. On Unix a thread created at launch waits for eventual exit, even following failed startup or termination. That thread counts towards the parent’s thread count and lives as long as the child. Keep each worker in its originating process. After a multithreaded fork, a child may use only async-signal-safe operations until exec. In the fallback using POSIX wait, leave the child’s status to this library. A Linux pidfd stays tied to the original worker through automatic or external reaping. Startup and request–reply have no overall deadline.

On Linux, a single-threaded worker can apply restrictions to the whole process. The kernel and local policy determine whether seccomp, Landlock and separate user, network and IPC namespaces are available. On macOS the worker requests the sandbox. On Windows the parent supplies `CreateProcessW` with an AppContainer and no network capabilities. The token is what the isolation report verifies. The parent creates a single-instance named pipe, and the worker opens it by its random name. The parent compares the connecting process ID with its worker before sending requests. The pipe grants access to the user and the AppContainer, so a process of the same user may compete for the connection. The parent disconnects a different PID. Repeated contention can prevent startup. Windows must allow application packages to read and execute the program and its libraries. The parent duplicates the creation handle with only termination and synchronization rights and closes the full handle before accepting a pipe client. The launcher still controls creation and executable selection. Applications that treat the parent as an adversary cannot rely on this launch protocol to keep worker memory from it.

`Worker::start_on_terminal` keeps the terminal on Linux and macOS, for a worker whose own code reads a password there. This crate reads none and changes no setting of the terminal: turning the echo off, checking that it is off and turning it on again are the program's to do. Such a program opens the terminal only for reading, since the filter refuses opening for writing, prompts on standard error, and changes the settings through standard error where that is the terminal: from Linux 6.10 the Landlock layer refuses every request to a device opened after it, so a terminal opened then can be read but not set up, and `open_channels` lists it as another device. Android and iOS start no worker: an Android app that wants one declares an isolated service (`android:isolatedProcess`) in its manifest, and its native code isolates its own thread there.

What a request and an answer hold is the program's protocol. The worker should answer with what the parent shows or saves, such as a finished carrier and a report, never the password, the key or the secret itself, unless the parent is the one to show it.

## Looking closer

`open_channels()` inspects the calling thread’s open descriptors, including standard streams, via `/proc/thread-self/fd` on Linux or `/dev/fd` on macOS. Each entry records its type and whether it is writable. An enumeration or classification failure makes the report incomplete or returns an error. Other threads sharing that table can still change it during inspection. Windows and WebAssembly report this operation as unsupported.

`Isolation::measures()` gives every protection with its outcome, whether it reaches the thread or the whole process, and what the call observed for that outcome, such as "a new socket was refused", "the call did not ask for it" or "the threads could not be read to look for a tracer". The words belong to the outcome: a protection that was not asked for or was refused never carries the proof of one that holds.

`run_on_protected_stack(bytes, required, work)` creates a Unix thread on a dedicated stack. Choose required properties from `locked`, `out_of_dumps` and `out_of_children`. If a property is missing, the call returns `StackError::NotProtected` before executing the closure. Apple platforms lack per-region dump exclusion. After joining the thread, the caller wipes the entire supplied stack, including unwritten bytes, then returns the result or resumes the panic. A failed join aborts the process. Registers, other threads, heap copies, closure captures on the caller and the returned value are outside the wipe. Avoid forking from any thread while the protected thread is alive. A continuing child can have a missing or zeroed stack and thread-local storage. Windows and WebAssembly do not implement this operation.

## Typing a secret

Where a secret first appears decides what protects it. An ordinary text field keeps copies of what is typed in buffers of its toolkit or web view, in its undo history and for screen readers, which no program can find and wipe. So:

- **In the terminal**, the worker started with `Worker::start_on_terminal` reads the password itself: the parent never holds it.
- **In a window**, send `Keystroke::Char`, `RemoveLast` or `Clear` to the worker and display its character count. `Keystroke::to_bytes` returns a value that wipes its bytes when dropped. The original character is a plain Rust value, and keyboard events still pass through the window system. A paste may place the complete secret in the clipboard or the GUI process. `SecretLine` holds the collected UTF-8 text in a fixed-capacity `Secret`.
- **A small native dialog** that alone asks for the password and hands it to the worker, as GnuPG's pinentry does, keeps even single characters out of the main window, but looks like no part of the program: it is a stricter mode for a program that wants it.

For example, a window can send keystrokes and carrier files to a worker and receive the finished files for saving. The application defines that protocol. A persistent key can stay in the worker, while keyboard and clipboard input still follow the platform input path.

## The secret writer

`write_secret(text)` writes to standard output past the standard library's buffer, which keeps the last bytes written and is never wiped: it flushes that buffer first, so that public output written before comes first, then writes the caller's bytes without a copy of its own. On a Windows console its UTF-16 copy lives in a `Secret`.

## What changed from the copies

The crate replaces two identical copies in `mhfe_core` and `stego-core`. Its first version moved them without changing what they do, with their tests, and then fixed five things a review found:

1. The macOS probe of file writes opened a predictable path with `File::create`, which could truncate a file, or the target of a link, at that path when the sandbox had not taken hold, and then removed the path. It now makes only a new file (`create_new`) and removes only what it made.
2. The descriptor of Linux secret memory was opened without `O_CLOEXEC`: a program that another thread started before the descriptor was closed would have got it.
3. The answers of `MADV_WIPEONFORK` and `minherit` were dropped, while the documentation promised that a child process gets none of the bytes. `is_out_of_children` now reports them.
4. Every call of `Isolation::enter` installed another seccomp filter and Landlock layer, which use up limits of the kernel. A thread that holds this crate's filter, from its own call or from the thread that started it, now gets no further layer. A filter that someone else installed does not count: the first check took any filter for this crate's, so that an Android app, which always runs under the system's filter, got none of this crate's.
5. Windows read the working set and set it again in two steps, so that threads making pages at once could lose a change, and every later drop gave back more than was taken. The two steps are now one, under a lock.

A probe of the channels out of an isolated process, run on Linux 7.0 in both an isolated thread and a process of one thread, then found what the copies left open, and the crate closes it: System V objects, which another program of the user saw by their key, and the keyring, from which another program read a test value; the dump flag, which code in the process could set again; datagrams through sockets opened before, from a process in an empty network too, since a socket keeps the namespace it was made in; signals to other processes; `execve`; and `userfaultfd`. The same review found that a refused filter was recorded as installed, so that a later call did not try again, and that the answer overstated some protections on Windows, on the Linux architectures without the filter and under a debugger.

Two security reviews of the draft then found what the draft itself got wrong, and each point is fixed with a test where Linux can run one. A worker reported its isolation after a cleanup of inherited descriptors that had failed, and kept a socket. The IPC namespace was asked for in a second call, which a system that restricts user namespaces, as Ubuntu does, refuses in the new one, so IPC stayed shared while the network read as empty. A `fork` while a secret was being made could inherit the descriptor of its secret memory. A tracer was looked for on one thread only. A parent that refused a long answer waited for a worker that waited to write. The detailed answer gave the proof of a protection that had not been asked for, a kernel without speculation control read as limited, and several Windows protections were applied without their result being read. The changelog lists them all.

## What is not covered

- Copies the program makes of a secret, stacks and registers, an image of the whole memory when the machine hibernates (except while Linux secret memory exists), and snapshots of a virtual machine.
- A process that exits through a signal, `abort` or `std::process::exit` can skip Rust destructors. The wipe is then skipped. Only the memory and dump protections actually granted by the OS still apply.
- Root, an administrator (`SeDebugPrivilege`), `CAP_SYS_PTRACE`, and a debugger or a `/proc/PID/mem` descriptor opened before the isolation; the answer says so for a debugger.
- On Linux, a socket connected before, which the program keeps on purpose. `sendmsg` on a socket opened before, whose address the filter cannot read, and file locks, which another program sees, stay unless the program turns on `Options::refuse_sendmsg` and `Options::refuse_file_locks`, since Wayland, D-Bus and SQLite need them. Without `Options::signals_to_self_only`, signals reach other processes on kernels before Linux 6.12 and on Android, and from 6.12 still the children the process starts.
- On Linux, a child made by a raw `clone` call while a secret is being made: the gate holds back `fork` only. Such a child also does not know the buffers it got from its parent as foreign.
- Using pre-fork references in a continuing child, or forking while any thread is using a protected stack.
- A program that unlocks its memory again after `Options::lock_all_memory`.
- In a process isolated in one thread, the other threads, which share its memory.
- A debugger outside the PID namespace of a container: it does not show there, so the reading of memory is unknown, never confirmed, in a PID namespace of its own.
- A worker that is slow to report or to answer: neither wait has a deadline.
- A worker on a system that does not list its open descriptors, such as Linux without /proc: it cannot show that its start was clean and is refused.
- On Windows, handles the worker itself opens before `serve`, and process or thread handles that another program obtained before isolation. The startup report inventories neither.
- A platform or runtime policy that denies both ways of closing inherited descriptors before Linux worker startup.
- An executable started outside `Worker::start` has no launcher guarantee. On Unix, `serve` rejects additional descriptors still open at the check. The Windows worker does not inventory handles.
- On Windows, a process of the same user that takes the worker's pipe again and again for a second: the start fails, and nothing was sent. Such a process may end the worker in any case.
- The physical copies a kernel can make when coalescing huge pages. Linux requests small pages for anonymous secrets and lets work areas use huge pages.
- On Windows, heap exclusion from error reports is requested without readback. Error reports can include thread stacks and registers. Network restrictions of the worker depend on AppContainer and system policy.
- On macOS, whether the sandbox refuses a new program is not probed, and on Linux for AArch64 the kernel offers no control of indirect branch speculation: both read as unknown, which the strict mode does not accept.
- On Android, the crash handler makes the process dumpable again for its tombstone.
- Covert channels that need no call the filter sees, such as the load of the processor or the timing of a shared cache.

## Tests

The unit tests check the buffers: what fits and what is refused, that truncating wipes, that the pages report locks, dump exclusion and child protection where each system gives them, that a zeroed secret is zero on every page, that guard pages lie on both sides of a secret and of a work area, that a closed secret opens only during a use, closes again after a use that panicked and remembers what its pages allow when the system refuses a change, that a work area the system cannot give is refused and a strict one is given only locked, that a closed secret says of its pages what its secret says, and that `Debug` hides the bytes of a secret, a work area and a key typed. They check that each option crosses to a worker as a bit of its own, that a refusal names each missing protection and every system explains a confirmation and a refusal in other words, and that every refusal of a buffer, a stack or a worker start says which it was. They also check the answer: that every byte value of a worker's report is taken only when it names an outcome and a reach, that each measure's words fit its outcome, how the kernel's speculation answers are read, and that a stack is wiped without reading bytes that were never written.

The three integration test programs use their own entry points to run isolated child roles. Each accepts `--skip <part of a name>`. Their shared runner can report a named check as skipped or partially exercised. Totals count named checks. The same-PID branch of the Linux memory-lock test runs only if `mlockall` succeeded and the system lets the child create a nested PID namespace. The test does not emit a separate skip for that branch.

- `isolation` checks from outside that an isolated thread is refused every call the filter names and keeps what it needs; that a datagram with an address is refused through a socket opened before, while a socket connected before still sends; that the dump settings cannot be undone; that no signal reaches a process outside the layer; that `speculation_limited` says what the kernel reads back; that a process of one thread is isolated as a whole, with IPC objects of its own; that further calls read back the same and add no seccomp filter, nor a call in a thread that an isolated thread started; that a process started under a filter of someone else's still gets this crate's, once; that a filter the system refuses is reported missing and tried again; that options refuse file locks and `sendmsg` with one more filter at most, and that `pidfd_send_signal` is refused; that a refusal by someone else's policy, without this crate's filter, confirms neither sockets nor programs nor file locks; that a PID namespace of its own leaves the reading of memory unknown, and that a child with its parent's number there does not take the parent's lock of memory for its own; that a Landlock layer refused once is tried again and recorded by one more filter; that a secret made where signals cannot be blocked takes no secret memory; that two threads that isolate themselves side by side get one filter each; that a lock of all memory is reported as the kernel answered, and by a later call; that a child made by `fork` takes neither its parent's signal rule nor its memory lock for its own, gets a rule of its own when it asks, and does not after an update of the filter that failed; that a thread does not report the signal rule of another thread; that a refused Landlock layer is not reported as a signal scope; that threads which cannot be listed leave the reading of memory unknown and stop a strict program; that speculation the kernel does not limit, or does not report, is not called limited; that a tracer on any thread makes the process readable; that a secret is written after the buffered public output, and that writing one where nobody reads fails and says so; and that the channels a process holds are listed by kind.
- `secret_memory` checks where the pages lie as the system reports them (locked, `MADV_DONTDUMP`, secret memory); that a secret works under every lock limit and says whether it is locked; that the strict constructors refuse what the limit does not hold; that a secret's anonymous pages stay small pages and a work area's do not; that under a quota partly used by another secret whatever they give is really out of swap; that a stack which must be locked is refused when nothing can be, and that a thread the system refuses is an error; that no child of two thousand forks made while another thread makes secrets inherits a descriptor of secret memory; that a process which had threads before its first secret takes no secret memory; that a secret made under a lock which a fork handler of the program waits for does not hang; that a work area lies on pages of its own; that six hundred secrets in a row each give back their error-report exclusion; that a secret beyond what the system gives ends the program as a full heap does; and that a child of `fork` drops its parent's secret, work area and closed secret without touching their pages, sees them reported as not held, ends when it reads one, and uses a secret of its own, while a closed secret of its parent's does not say it is closed (Linux and macOS).
- `worker` starts the test program as its own worker and checks that it answers isolated; that it has no environment, descriptor or terminal of its parent's but its pipes, its standard error /dev/null, or its parent's on the terminal; that it applies the options it is given; that a worker lacking a required protection is stopped before any request; that an answer too long for a pipe, once refused, ends the worker before the call returns; that a request beyond the worker's limit ends it, at once also when the worker's process lives on; that forced shutdown requires a stable kernel handle and a surviving Unix child is collected on exit; that a worker serves once; that a program which opened a file before it called `serve` keeps it and says that its start was not clean; that a text in the worker's variable which is no setting, numbers of descriptors included, starts no worker and closes nothing; that a program which may not signal others leaves such a worker behind, in time, and says so; that a program which reaches the start of a worker before `serve` starts none; that a worker starts from a protected stack, and of each kind from a program whose standard streams are closed; that the code a worker runs before `main`, as a library's start-up code, finds no pipe its parent left open; that a worker which cannot list what it holds, cannot leave the session, or dies before it reports is refused; that a program which ignores SIGCHLD still ends its worker; that a descriptor which cannot be looked at is listed as unknown, in a list that says it is not whole; that without /dev/null a worker which serves no more still ends its streams and keeps their numbers; and, on Windows, that another process which takes the pipe first does not stop the start.

The tests run on Linux for x86-64 and AArch64, on macOS and on Windows, at every push (`.github/workflows/ci.yml`): the unit tests and the three test programs, as far as each system has the code. On macOS that is the pages, the sandbox and the worker; on Windows the pages, the mitigations and the worker in its AppContainer, with its named pipe. What follows was done on Linux for x86-64. Each fix of the reviews that a test can tell apart was checked by removing it, and a test fails for each; the wipe of a stack through `MaybeUninit` is the exception, since it writes the same zeros as the wipe before it. Beyond `cargo test`, Miri runs the unit tests that make no system call, the wipe of an unwritten stack among them; AddressSanitizer runs every test but those that check locked memory against the kernel, since it puts its own `mlock` in, which locks nothing; its leak check is off in the test programs, since it needs `ptrace`, which an isolated process refuses, and its log must hold no sanitizer report from any process; `cargo audit` checks the dependencies; and the release build keeps the instructions that write zeros in `Secret::truncate`, the drop of a `Secret` and of a `WorkArea`, and the wipe of a stack. [Test coverage](COVERAGE.md) has the measured lines. Clippy checks the crate for Linux, Android, macOS, iOS, Windows and WebAssembly; the code for Android and iOS is not run anywhere yet.
