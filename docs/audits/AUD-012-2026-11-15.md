# AUD-012 — Final release audit of secret-protection-core

## Release decision

**BLOCKED for native integrations in which a linked library can close and reuse an inherited descriptor during initialization.** One reproducible Medium finding is open: `AUD-012-SEC001`. No direct secret disclosure was demonstrated, but the worker's documented descriptor-ownership boundary is broken. The finding must be fixed and its retained harness must pass before such integrations are released.

All other executed release checks were green, except that the documented coverage percentage was not reproduced exactly: the independent run measured 91.21% and recorded two profile-write refusals from isolated processes. This is a measurement limitation, not a test failure or evidence of a security defect.

### Finding

#### AUD-012-SEC001 — Medium — Worker pre-main cleanup closes a descriptor reused by a linked library

- **Status / release blocking:** Open; blocking for native integrations that permit this constructor behavior.
- **Affected files and builds:** `src/os/unix.rs:352-390`, `src/worker.rs:254-259`, `docs/TECHNICAL.md:160`, `tests/worker.rs:566-604`; Unix worker startup, reproduced on Linux. Related to the original cleanup issue `AUD-010-SEC002`, but concerns the revised named-number mechanism.
- **Reproduction:** Link a shared library with an initializer that closes the inherited descriptor and opens its own `/dev/null`, reusing its number. Start the program with a valid worker setting naming that descriptor. The retained two-crate harness does this through the real dynamic-library initialization order.
- **Expected:** The initializer closes only descriptors inherited from the parent; a descriptor opened by the linked library remains its own, as `docs/TECHNICAL.md` promises.
- **Observed:** The library constructor reused the number, then the crate's `before_main` closed that number. The child's check failed, and the parent harness exited 1.
- **Impact:** A native dependency loses its own descriptor and can malfunction or read/write the wrong resource later. The cleanup may then make the worker appear clean because the reused descriptor is gone. No direct disclosure of a parent secret was observed; this is an ownership and compatibility defect with security-boundary relevance.
- **Evidence:** `AUD-011-harnesses` was renamed to `AUD-012-harnesses` when the report number changed; its final source passes clippy. The final runtime log and command JSON are local evidence.
- **Recommended fix:** Perform inheritance cleanup at the spawn/exec boundary, before library constructors, using the existing ordinary-stack launcher, or replace numeric post-constructor cleanup with a design that preserves object identity. Merely checking the number again after constructors cannot distinguish reuse.
- **Required verification:** The retained harness must pass after the fix; run the full native worker suite on Linux and macOS, including ordinary inherited descriptors, descriptors opened by libraries, no-op malformed settings and protected-stack launch.

### Confirmed improvements and remaining risks

- Fork-generation tracking now prevents inherited buffer owners from touching absent or zeroed pages in a continuing child, reports their protections as absent and permits fresh child-owned buffers. Pre-fork borrowed slices and raw `clone` remain explicitly outside the guarantee.
- Worker startup now refuses unclean descriptor states, malformed settings and recursive worker creation. Calls use bounded frames and one bounded teardown operation. Report and response I/O deliberately have no deadline.
- Windows workers inherit no handles and use a random named pipe with peer-PID checking. Repeated same-user pipe contention remains an accepted availability risk, not a secret-confidentiality finding.
- The report's `Outcome` model and strict mode consistently reject `Unknown`, `Refused`, `Unsupported` and `NotRequested`.
- WebAssembly's heap fallback accurately disclaims native page protections.
- All historical findings not explicitly listed as accepted or platform-pending were checked against current source and the full test suite; no additional defect was confirmed.

### Assessment and limitations

The signed source has broad and mostly successful verification: full debug/release tests, native CI on four runners, six clippy configurations, fuzzing, ASan, Miri, WebAssembly runtime, dependency audits and release disassembly. Nevertheless, one reproducible ownership defect prevents an unqualified release recommendation for affected native integrations.

Android and iOS were not run on devices. macOS and Windows evidence comes from the exact-SHA CI, not local execution. The WebAssembly check uses Node/V8, not a browser application. Coverage measurement does not reproduce the documented 97.41% and must not be cited as independently confirmed; the documented source fingerprint itself was verified as `db750b5041779ce841332935b6fbbb5067be931c62b5dbeda41ba67fb31a5808`.

There is no canonical binary reproducibility procedure, release tag, published release or registry package in this snapshot. No claim is made of exhaustive memory erasure, absence of all vulnerabilities or independent cryptographic certification.
