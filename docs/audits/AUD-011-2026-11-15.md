### Findings

#### AUD-011-API001 — Low — `ClosedSecret::is_closed` does not check `pages.here()` after `fork`

- **Category:** API.
- **Severity:** low.
- **Status:** open.
- **Release blocking:** false.
- **Affected files and builds:** `src/protect/closed.rs:94-97` (Unix builds).
- **Reproduction:** Create a `ClosedSecret`, `fork()`, and inspect `closed.is_closed()` in the continuing child process alongside `closed.is_locked()` and `closed.is_out_of_children()`.
- **Expected behavior:** Consistent with `ClosedSecret::is_locked`, `is_out_of_dumps`, and `is_out_of_children` (which all return `false` in a post-`fork` child because `self.secret.pages.here()` is `false` and the pages were dropped/unmapped or wiped by the kernel), `is_closed()` should not report that pages are closed in a child where the buffer is no longer held.
- **Observed behavior:** `ClosedSecret::is_closed(&self)` returns `self.access == Access::Nothing` without checking `self.secret.pages.here()`, so on Linux (`memfd_secret` + `MADV_DONTFORK`) and macOS (`VM_INHERIT_NONE`) it still returns `true` in the child even though no pages exist there. Attempting `read`/`write`/`push`/`truncate` in the child still safely aborts via `region()` -> `check()`.
- **Impact:** Minor API inconsistency in post-`fork` status reporting; no secret exposure or undefined behavior.
- **Evidence:** Inspection of `src/protect/closed.rs:94-110` vs `src/os.rs:163-185`.
- **Recommended fix:** Return `self.secret.pages.here() && self.access == Access::Nothing` from `ClosedSecret::is_closed(&self)` and extend the fork test in `tests/secret_memory.rs` to assert `!closed.is_closed()` in the child.
- **Required verification:** `cargo test --test secret_memory` on Linux and macOS.

- **AUD-011-ARC001 (`tests/worker.rs` size):** `tests/worker.rs` currently contains 790 non-blank, non-comment lines (977 total lines), leaving only 10 LOC of headroom below CORE-15's 800-line ceiling. Future worker tests should split `tests/worker.rs` into `tests/worker/main.rs` + platform submodules (matching `tests/isolation/`).
- **Multithreaded parent `Worker::start` descriptor race:** As documented in `src/os/unix.rs:312-315`, `left_open()` snapshots non-`FD_CLOEXEC` descriptors in the parent before `command.spawn()`. Any descriptor opened without `FD_CLOEXEC` between those calls causes `starts_clean()` to safely refuse the worker (`WorkerError::Unclean`). In the converse race (a parent thread closes a non-`FD_CLOEXEC` descriptor in that window while a worker's third-party C library `.init_array` constructor opens a file reusing that exact number before `before_main`), `before_main` could close the library's descriptor. Single-threaded or disciplined `FD_CLOEXEC` parent code avoids this.
- **Unreachable fallback paths (covered by code review, not execution):** The 59 uncovered lines in Linux x86-64 `llvm-cov` (2.59%) correspond exclusively to OS failure paths (`mmap`/`mprotect`/`madvise`/`pthread_atfork`/`dup2`/`pthread_join` failures, 4 GiB+ frame sizes, >1s worker kills, and second `serve` in-process branch). Inspection confirms fail-safe behavior (`out_of_memory`, `abort`, error returns).

### Assessment and limitations

1. **Tested coverage vs. security certification:** Local execution on Linux x86-64 (kernel `7.0.0-43-generic`) independently verified 97.41% line coverage (2,217 / 2,276), 14 Miri tests, 72 ASan tests (4 documented `mlock` skips), 4.79M libFuzzer runs, release `.rlib` volatile zeroization disassembly, and WebAssembly Node.js execution. Native CI run `43718908771` verified Linux AArch64, macOS, and Windows Server 2025 execution on `2747028f`.
2. **Untested platforms at runtime:** Android (`aarch64-linux-android`) and iOS (`aarch64-apple-ios`) targets are compiled and Clippy-checked with `-D warnings` but have no hardware/emulator runtime execution.
3. **Documented platform exclusions:** Raw `clone(2)` calls bypassing `pthread_atfork`, pre-fork borrowed slices used in a continuing child, pre-isolation attached debuggers/`/proc/PID/mem` fds, external container PID namespaces, hibernation/VM snapshots (except Linux `memfd_secret`), and CPU microarchitectural covert channels remain explicitly outside the crate's threat boundary as documented in `docs/TECHNICAL.md`.
