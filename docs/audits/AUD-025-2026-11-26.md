### Findings

#### AUD-025-API001 — Low — The optional pidfd launch can follow an expired deadline

**Expected.** Each process-creation attempt is preceded by an absolute deadline check after potentially blocking preparation.

**Observed.** Before trying the optional pidfd launcher the code first resolves it with dlsym. glibc serializes lookup with concurrent library changes. The deadline check before the helper precedes that lock. The ordinary posix_spawn fallback has its own check.

**Impact.** If lookup takes the remaining budget, the first launch attempt can start after the deadline. Later disposal and collection still apply.

**Suggested fix.** Recheck the existing deadline after symbol resolution and immediately before using the optional launcher.

**Verification.** Exercise deadline exhaustion between an independently controlled symbol-resolution result and the attempted launch.

### Assessment and limitations

- The six short release campaign results for this candidate are missing. The long GitHub campaign is a later tag stage. Local campaigns were left stopped. Tagged provenance and attestation are evaluated during the tagged phase.
- Android, iOS, iOS Simulator and ARMv5 are compile-only in this evidence and have no app/device run. Native host Linux tests cannot supply those platform guarantees.
- On the hosted Linux runners the nested PID namespace subcase is partial. Two i686 secretmem cases are ignored. Real Windows console and the named macOS access-list, mount and special folder probes remain unverified.
- Native optimized stack tests use the Rust test harness. The test report covers the measured wipe paths and does not establish linked panic-abort, hardware erasure or general side-channel resistance.
- Miri was limited to portable operations without native OS interaction. ASan excludes the four native lock assertions that its own lock interceptor changes, and leak checking is disabled. See individual runtime logs.
- Cargo-deny bans and sources and RustSec cached advisories were checked separately. The offline cargo-deny advisory database checkout is missing.
- Cargo careful, Kani and loom are not installed in the workspace toolchain. Native OS authority was checked by source and applicable platform tests.
- Approval review blocked executing the external cargo-semver-checks binary again, despite its registry install record and the offline baseline. AUD-024 retains the earlier default verification; this audit does not claim a fresh exact-candidate run.
- The source was audited with lexical site inventories. The per-site semantic/runtime evidence ledger and re-execution of every earlier conditional case remain incomplete.
- The initial TSan protected-stack test fails its OS lock read-back under a runtime that explicitly ignores mlock. The separate synthetic concurrent probe covers four public stack and buffer allocations with the supported assertions.
