# AUD-021 — Pre-release audit of secret-protection-core 0.2.0

## Release decision

**FAIL.** The Linux worker transport does not enforce private endpoints for ordinary same-user peers under the affected host policy. Native mapping sizes can violate the Rust slice invariant on 32-bit targets. Fix and verify both before release. The final tagged and attested cargo package remains a release gate.

### Findings

#### AUD-021-SEC001 — High — Linux worker pipes are exposed through the launcher

- **Status** Open. **Release blocking** Yes.
- **Affected implementation** [`src/os/unix/worker.rs:70–76,105–109`](../../src/os/unix/worker.rs#L70), [`src/worker.rs:125–157,231–279`](../../src/worker.rs#L125), [`docs/TECHNICAL.md:108–115`](../../docs/TECHNICAL.md#L108), [`SECURITY.md:19`](../../SECURITY.md#L19).
- **Expected** Only the launcher and its worker should have access to the private request/reply channel and startup report.
- **Observed** The Unix launcher retains two ordinary pipes. On Linux their inodes can be reopened by a separate process with matching credentials when the launcher is dumpable and procfs and the LSM allow it. The worker's own restrictions leave the launcher ends unchanged. The receiving side validates report bytes and framing but assumes exclusive endpoints.
- **Impact** Local confidentiality and message integrity can be lost for data sent through the pipes, including the startup admission report and forwarded secret data. A peer can also invalidate the assumption of exclusive I/O during a timed exchange. This requires ordinary same-user access as permitted by host policy; privileged debugging and application code execution are unnecessary. Secrets held entirely within the worker do not cross these pipes.
- **Evidence** Independent source traces and the Linux procfs and ptrace ABI. Yama attach restrictions alone leave the descriptor read-mode check outside their scope. A parent-side dumpability check alone also leaves a worker initialization interval because ordinary exec restores its dumpable flag. No live interception test was performed.
- **Proposed correction** Use a transport that preserves endpoint ownership over both launcher and child lifetimes. Document the parent-process trust boundary and make startup and timed I/O rely on enforceable transport properties.
- **Verification** Verify endpoint exclusivity from process creation through teardown under the supported Linux policies. Retest the ordinary synthetic worker protocol and timed I/O.

[Linux procfs descriptor permissions](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html) · [Linux ptrace access modes](https://man7.org/linux/man-pages/man2/ptrace.2.html) · [Yama roles](https://docs.kernel.org/admin-guide/LSM/Yama.html) · [Linux execve process attributes](https://man7.org/linux/man-pages/man2/execve.2.html)

#### AUD-021-SEC002 — Medium — Native allocation accepts sizes outside Rust slice limits

- **Status** Open. **Release blocking** Yes.
- **Affected implementation** [`src/os/unix.rs:165–190,452–459,499–501`](../../src/os/unix.rs#L165), [`src/os.rs:151–158,190–203`](../../src/os.rs#L151), [`src/protect.rs:182–213`](../../src/protect.rs#L182).
- **Expected** The native mapping boundary guarantees that every Rust slice built from its mapping is at most isize::MAX bytes, and fallible API paths reject unsupported sizes before mapping.
- **Observed** Unix reservation bounds page rounding and guard-page arithmetic in usize but omits the isize::MAX contract. Allocation owners and stack wiping form raw slices from the stored native length. Linux mmap can accept an object larger than PTRDIFF_MAX, the corresponding C limit.
- **Impact** Unsound safe API if a 32-bit process can reserve enough contiguous virtual address space. Documented Linux 32-bit support is affected conditionally. The Windows native boundary likewise relies on OS refusal, although the tested 64-bit configuration has a much smaller usable address range than isize::MAX. No runtime undefined behavior was observed.
- **Evidence** Two independent static reviews, the Rust slice safety contract and the mmap contract. Existing oversized WorkArea test passes on x86-64 and cross-Clippy succeeds on ARMv5; neither establishes that the crate itself rejects the size before a native reservation on a 32-bit host.
- **Proposed correction** Enforce the slice-layout size bound in the common native allocation contract, including the protected stack's wipe length after rounding and each raw-slice call site.
- **Verification** Exercise the size validation independently of allocator success and run the bounded regression on 32-bit native Linux.

[Rust slice safety contract](https://doc.rust-lang.org/std/slice/fn.from_raw_parts.html#safety) · [Linux mmap caveats](https://man7.org/linux/man-pages/man2/mmap.2.html#CAVEATS)

#### AUD-021-API001 — Medium — Timed worker start traps on WebAssembly

- **Status** Open. **Release blocking** No.
- **Affected implementation** [`src/worker.rs:86–96`](../../src/worker.rs#L86), [`src/os.rs:275–302`](../../src/os.rs#L275), [`docs/API.md:306–325`](../../docs/API.md#L306).
- **Expected** Worker start methods report Unsupported on wasm32-unknown-unknown.
- **Observed** The timed variant calls Instant::now before reaching the unsupported-platform implementation, resulting in a WebAssembly trap. The ordinary start and terminal variant reach the unsupported path.
