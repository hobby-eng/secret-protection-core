### Finding

#### AUD-005-DOC001 — Low — Existing Windows job need not confirm the documented one-process limit

- **Status / release blocking:** Open; non-blocking.
- **Affected files and builds:** `src/os/windows.rs:461-517`, `docs/TECHNICAL.md:115`; Windows, statically reviewed.
- **Reproduction:** Place the process in a job that already has all `DESKTOP_LIMITS` but has no `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` limit of one, then call `Isolation::enter()`.
- **Expected:** If the technical notes say the job allows only one process as a second line behind child-process policy, that limit is read back and confirmed.
- **Observed:** `desktop_limits_hold()` queries only `JobObjectBasicUIRestrictions`. When those limits hold, `enter_restricted_job()` returns immediately without querying `JobObjectBasicLimitInformation` or checking `ActiveProcessLimit`.
- **Impact:** The documented second job restriction is not established for a pre-existing job. The separate `NoNewPrograms` mitigation is still read back, so this is a bounded documentation/reporting defect rather than a demonstrated process-creation bypass.
- **Evidence:** Direct source/document comparison; no Windows runtime was available.
- **Recommended fix:** Query basic job limits and require `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` with `ActiveProcessLimit == 1`, or remove/qualify the second-line claim.
- **Required verification:** On Windows, test a pre-existing UI-restricted job without an active-process limit, a correctly limited job and policy-assignment failure.

### Independent confirmation of existing findings

- **AUD-003-SEC003 — Medium — Signal-filter ownership is recorded before installation succeeds.** The public-API probe first installed `signals_to_self_only`, then refused every later `PR_SET_SECCOMP`. After `fork`, the child requested the additional `refuse_sendmsg` option. The failed upgrade returned the inherited filter but still produced `Confirmed`. Signal 0 to the child itself failed, while signal 0 to its parent succeeded. This is a live confirmation of wrong ownership and an actual foreign-process signal permission, not merely a stale message. `SIGNAL_OWNER` should be updated only after successful installation, with this regression retained.
- **AUD-003-DOC001 — Low — Obsolete seccomp marker.** The implementation uses `MARK = 0xE00` (3584) with eight payload bits at `src/os/linux.rs:725-734`; `docs/TECHNICAL.md:87` still says 4001. Confirmed without a new ID.
- **macOS follow-up, not a finding:** `enter()` now calls `sandbox_init` before `ptrace(PT_DENY_ATTACH)` at `src/os/apple.rs:22-23`, reversing the previous order. Whether this profile permits that ptrace operation is unresolved without macOS. Add an explicit runtime assertion for `NoMemoryReading` before relying on the worker there; no defect is claimed without that evidence.

### Assessment and limitations

The main remediation path works on Linux: worker admission waits for a clean report, IPC namespaces are separate, strict mode accepts only `Confirmed`, large-answer teardown returns, protected-stack properties are enforced before work, and the stock 44 checks executed here pass. One new Low documentation/read-back mismatch was found. An existing Medium signal-ownership defect was reproduced end to end and remains a strict-use concern until fixed.

Windows and macOS were not executed; Android, iOS and WebAssembly were also not run. No new six-target clippy matrix, sanitizer, Miri, assembly, coverage, mutation or advisory campaign was repeated. Those results in AUD-003/AUD-004 are comparison evidence, not independent reruns by this review. This report is not a security certification or release acceptance.
