### Findings

#### AUD-002-SEC001 — High — Worker keeps inherited channels when both descriptor-closing methods fail

- **Status / release blocking:** Open; blocking for any use that relies on the worker's descriptor boundary.
- **Affected files and builds:** `src/os/unix.rs:249-276`, `src/worker.rs:140-152`; Unix workers, reproduced on Linux. Windows uses an explicit handle list instead.
- **Reproduction:** Start with an inheritable synthetic socket. Refuse `close_range` through an earlier seccomp filter and provide a minimal `/proc` with `self/exe` but no `self/fd`. Start the public `Worker` API and ask it to use the inherited descriptor.
- **Expected:** The worker inherits only its standard pipes, or startup fails before isolation/reporting and before any request.
- **Observed:** `close_range` failed, `read_dir` failed, and `close_inherited()` silently returned. The worker started, retained the socket and wrote byte `[120]` through it after isolation.
- **Impact:** An inherited connected socket, writable file or other descriptor remains a direct secret-egress channel despite the documented “only its pipes” boundary. The prerequisites are realistic in restricted containers and seccomp-confined programs.
- **Evidence:** `inherited-fd` harness and local exit-1 log; README claim at `README.md:77-83` and protocol description at `docs/TECHNICAL.md:123-129`.
- **Recommended fix:** Make descriptor closure fallible and fail worker startup when both methods cannot complete. Do not send a successful isolation report after a closure failure. Keep the synthetic no-`fd` regression.
- **Required verification:** Repeat the live-socket probe, verify ordinary `close_range` and `/proc`/`dev/fd` fallbacks, and run the worker suite on Linux and macOS.

#### AUD-002-SEC002 — Medium — Sequential namespace calls leave IPC shared while network isolation succeeds

- **Status / release blocking:** Open; blocking because the stock isolation test fails and the documented IPC boundary is absent.
- **Affected files and builds:** `src/os/linux.rs:109-154` and `src/os/linux.rs:301-316` at the reviewed commit; single-threaded Linux.
- **Reproduction:** Compare `/proc/self/ns/ipc` before and after `Isolation::enter()` on a system permitting user/network namespaces. Independently, `unshare -U -n` followed by `unshare -i` returned `EPERM`, while combined `unshare -U -n -i` succeeded.
- **Expected:** A successful own-network result also creates the documented own IPC namespace, or the missing IPC protection is explicitly reported.
- **Observed:** `CLONE_NEWUSER | CLONE_NEWNET` succeeded; the subsequent `CLONE_NEWIPC` failed and its result was discarded. `empty_network` was true while the IPC inode remained `4026531839`. `cargo test` failed at `tests/isolation.rs:1023`.
- **Impact:** IPC objects remain shared. On x86-64/AArch64 the seccomp System V IPC and POSIX-queue blocks reduce the immediate impact; other architectures lack that filter. The failed mandatory test also makes the baseline non-green.
- **Evidence:** Harness `ipc`, baseline test output and independent namespace command.
- **Recommended fix:** Request user, network and IPC namespaces in one `unshare` call and avoid nested re-entry once the owned namespaces are established. If IPC is to remain independently optional, report it separately rather than hiding failure.
- **Required verification:** The existing whole-process test plus positive/negative System V IPC and POSIX-queue probes on filtered and unfiltered architectures.

#### AUD-002-SEC003 — Medium — Several advertised Windows protections discard their read-back results

- **Status / release blocking:** Open by source inspection; blocking for Windows use until corrected and run on Windows.
- **Affected files and builds:** `src/os/windows.rs:271-315`, `src/os/windows.rs:380-452`; Windows.
- **Reproduction:** On a Windows version or policy context that refuses one of these operations, call `Isolation::enter()` and inspect the returned fields/measures. Static control flow already shows that no caller-visible state can represent these failures.
- **Expected:** Every advertised protection is confirmed and reported, or its failure is visible; a missing mandatory protection is usable with `enter_requiring`.
- **Observed:** Results of extension-point, image-load and child-process mitigations are discarded. Job creation, both `SetInformationJobObject` calls and `AssignProcessToJobObject` are ignored. `lower_integrity` returns a read-back result that is also discarded. DLL-search and WER calls are unchecked. These operations have no corresponding `Protection` values.
- **Impact:** Callers can rely on documentation saying these protections applied even when Windows refused them. This audit did not execute Windows and therefore does not claim which operations fail on a particular Windows build.
- **Evidence:** Direct source trace; contrast the used read-backs for dynamic code/signature/DACLs with the discarded results above and the report principle at `docs/TECHNICAL.md:23-29`.
- **Recommended fix:** Expose each retained protection's confirmed state (or stop advertising it), include failures in strict mode and `measures`, and check job assignment/configuration rather than only creation.
- **Required verification:** Runtime success and forced-failure cases on supported Windows versions, including child creation, clipboard/UI restrictions, image loading and integrity read-back.

#### AUD-002-FUN001 — Medium — Dropping a worker after an oversized answer can deadlock both processes

- **Status / release blocking:** Open; blocking for the worker API.
- **Affected files and builds:** `src/worker.rs:92-129`, `src/os/unix.rs:242-246`, `src/os/windows.rs:784-791`; all worker platforms.
- **Reproduction:** Let `serve` return a 1 MiB synthetic answer, call `Worker::call(request, 1024)`, receive `InvalidData`, and drop the worker. A watchdog expires after three seconds.
- **Expected:** Oversized-answer handling and `Drop` terminate the worker and return without draining an unbounded frame.
- **Observed:** The parent retains the read pipe but stops reading. The child blocks writing the large answer; `Drop` closes only child input and waits while the parent read pipe remains open. The watchdog fired.
- **Impact:** A size limit intended to bound work can instead hang the calling program permanently during ordinary error cleanup.
- **Evidence:** `worker-drop` harness and local watchdog log. The stock 100-byte test passes because it fits in the pipe and misses the blocking case.
- **Recommended fix:** Close/shutdown the parent's read channel before waiting and ensure the child is terminated/reaped if it does not exit. Mark the protocol broken on partial-frame I/O failures as well.
- **Required verification:** Answers above pipe capacity on every worker platform, partial frames, child exit during writes, and repeated `Drop`/error paths without hangs or leftover processes.

#### AUD-002-API001 — Low — Overflowing protected-stack size panics instead of returning an error

- **Status / release blocking:** Open; non-blocking.
- **Affected files and builds:** `src/os/unix.rs:355-358`; Unix `run_on_protected_stack`.
- **Reproduction:** Call `run_on_protected_stack(usize::MAX, || {})` and catch the result.
- **Expected:** The `io::Result` API returns an allocation/size error.
- **Observed:** `bytes.next_multiple_of(page_size())` panics with `attempt to add with overflow` before the checked `WorkArea` allocation path.
- **Impact:** An invalid size causes a bounded, caller-triggered panic rather than a usable error; no memory corruption or secret disclosure was found.
- **Evidence:** `stack-overflow` harness and local log.
- **Recommended fix:** Use `checked_next_multiple_of` and map overflow to `InvalidInput` or `OutOfMemory`.
- **Required verification:** `usize::MAX`, page-boundary sizes, zero and the minimum pthread stack on supported Unix targets.

#### AUD-002-DOC001 — Low — Technical notes still describe shipped options as future work

- **Status / release blocking:** Open; non-blocking.
- **Affected files and builds:** `docs/TECHNICAL.md:167-184`.
- **Reproduction:** Compare the limitations/tests sections with `Options` and the three integration-test programs.
- **Expected:** Documentation describes the current snapshot consistently.
- **Observed:** Line 172 says `sendmsg` and file locks are “to become options” and signals are refused only from Linux 6.12, although both options and `signals_to_self_only` are implemented. Line 182 says “Two test programs” although `isolation`, `secret_memory` and `worker` exist. The test inventory omits several new checks.
- **Impact:** Readers can misunderstand available protections and actual coverage; no direct runtime impact.
- **Evidence:** Source/document comparison.
- **Recommended fix:** Describe existing options in the limitation, change the count to three and list signal, lock-all, channel, measures and protected-stack coverage, including the new negative regressions from this audit.
- **Required verification:** Documentation review against the final API and test list; no build required for text alone.

### Informational observations and recommendations

- `signals_to_self_only` passed the dedicated seccomp-only probe: `pidfd_send_signal` is unconditionally refused, while own-process signal rules remain separate. No defect is reported for the signal syscall numbers.
- `lock_all_memory` correctly reports the `mlockall(MCL_CURRENT | MCL_FUTURE | MCL_ONFAULT)` result and is reasonably excluded from the default option set. Review whether later `munlock`/`munlockall` and `setns` calls should be refused if “for good” must hold against code that explicitly undoes the isolation; no runtime finding is claimed here.
- `open_channels` is a non-atomic `/proc`/`dev/fd` traversal and silently drops descriptors whose `fstat` fails. Document its snapshot/race semantics or expose partial/unknown status if callers will make security decisions from it.
- `serve` accepts any 32-bit request length and allocates before reading the request body. A configurable request bound would reduce avoidable worker OOM/availability risk; the parent is otherwise the trusted protocol peer.
- On Windows, test concurrent process creation while worker pipes exist. Child ends are inheritable before `CreateProcessW`; another child spawned by the parent at the wrong time could inherit them unless all spawn paths use explicit handle lists.
- No assembly-level proof was added for wiping. The source consistently uses `zeroize` over the complete owned slices before releasing pages, and no custom wiping bypass was found.

### Assessment and limitations

The reviewed snapshot is **not ready for integration as a protection boundary**. One high-severity inherited-channel defect, two medium security-reporting/isolation defects and a deterministic worker deadlock are open. The baseline full test command is red. The signal option, ordinary memory protections, normal protected-stack behavior and six-target clippy matrix produced useful positive evidence, but they do not offset those findings.

Windows and macOS runtime behavior remains unverified; Android/iOS were not executed. No claim is made about absence of all vulnerabilities, compiler-level erasure in every optimization context, upstream dependency internals or production readiness. This is a source and Linux-runtime security audit, not an independent cryptographic certification or a release acceptance.
